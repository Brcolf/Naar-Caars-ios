## Findings from the owner-present run

- **G1. A Town Hall photo that arrives while the feed is off screen downloads and cancels once per frame (new in this run; cause not proven).** The owner's device logged `Failed to download image: NSURLErrorDomain -999` 4,795 times from 14:23:14.05 to 14:24:35.20 PDT, one about every 16.7 ms. The run started 0.3 s after `[townHall] completed(… ins=1 …) trigger=push:town_hall_post` inserted the review post into the Community tab's feed, which was showing P5b Live Check but was not on screen. It stopped when My Reviews downloaded the same image. The second photo post reproduced it: the 14:32:48 safety poll inserted it, and 4,278 lines followed until the Community tab was opened at 14:34:05. None of these attempts reached the server (one sign POST, no GET, until the tab opened); the app used 26 % CPU. A `sample` during the run shows `CachedAsyncImage.body` / `loadImage` (`NaarsCars/UI/Components/Common/CachedAsyncImage.swift:44-72`) under `TownHallPostCard.regularPostContent`, and `PersistentImageService.getImage` at the download and the error log (`NaarsCars/Core/Services/PersistentImageService.swift:103`, `:124`). When the tab opened, the card showed the error placeholder instead of the photo (capture 17): the last cancelled attempt set `hasFailed`, and `.task(id: url)` does not run again for the same URL. Leaving the tab and coming back re-created the card and loaded the photo (capture 18). Likely mechanism, not proven: `loadImage` resets `hasFailed` to false at its start, which brings back the spinning `ProgressView` placeholder; in the hidden tab's lazy stack the card then disappears and reappears every frame, so the task is cancelled and started again. Last night's owner log (the 5a build, before `8606c8e`) has no such line despite two `push:town_hall_post` inserts; whether the hidden-tab condition was the same then is not known. Candidates among today's commits: `8606c8e` / `4812026` (`CachedAsyncImage`, display-size decode), `8a8b867` / `5e91b00` (feed re-entry), `138538f` (sync writes off the main actor). Fix direction: do not restart a load for a URL whose last attempt was cancelled rather than failed (treat `CancellationError` / -999 as "not tried"), and do not put up the spinner again for a retry; then repeat this check. **Fixed in `48bd1ee`.** Cause, confirmed with temporary logging on the device: the `.task` on a `Group` (`CachedAsyncImage.swift:55`) restarts on every branch switch, a card inserted into the hidden tab appears and disappears at once, and the cancelled load set `hasFailed` (`:80`) while the next one reset it (`:69`), once per frame, with the `isLoading` guard (`:67`) leaving the error view when the tab opened; a load now writes no state when it starts or is cancelled and the guard is gone, and the same hidden insert logged 1,613 -999 lines in 27 s before and 1 in 30 s after (CPU 0 %), with the photo shown when the tab opened. The loop's code predates this phase's commits (`0af6e16` has the same body); the 5a build was not run.
- **G2. The inline "Requests to join" row in My communities does nothing (pre-existing since Phase 2).** Two taps at 13:46:50 and 13:47:05 PDT did not push the screen (log: `fetchCommunityMembers failed: cancelled`). The row is `NavigationLink(value: PendingMembersTarget…)` (`NaarsCars/Features/Community/Views/MyCommunitiesView.swift:397`), resolved by `.navigationDestination(for: PendingMembersTarget.self)` (`:127`) inside a screen that is itself pushed (`NaarsCars/Features/Profile/Views/MyProfileView.swift:212`, `navigationDestination(isPresented:)`; a destination-style link before `4f3e246`). That is the pattern CLAUDE.md records as broken (Phase 3, `930e906`). The row appears only when the count is above 0, which is why earlier gates went through the ••• menu. Fix: have the row set `pendingTarget`, the item-driven destination at `:131` that the ••• menu uses (`:370`). **Fixed in `e0f3670`.** The row is now a Button that sets `pendingTarget` (the value-based destination, used only by it, is removed); on the owner's iPhone 16, with a local uncommitted build that showed the row with a count of 1 (no community has a pending request), the row opened Requests to join.
- **G3. 5a F3 is still open when the viewer leaves the community** (pre-existing; `5970e9f` covers only part of it). The trigger and the evidence are in the table above (capture 19). It is the case the 5a report predicted: the row disappears from a list that pushes through a view-destination `NavigationLink` (`NaarsCars/Features/Requests/Views/RequestsDashboardView.swift:218`), and the pushed screen ends up drawing none of the branches at `NaarsCars/Features/Rides/Views/RideDetailView.swift:69-89`. Fix, as the 5a report said: push rows through the dashboard's item-driven `navigationDestination(item: $selectedRideId)`. `FavorDetailView` has the same gap.
- **G4. A deleted account's photos stay in the device's image cache (pre-existing, known follow-up; now more relevant).** After the deletion, the iPhone 17's `Library/Caches/PersistentImageCache` still holds the four photos the throwaway sent today (message, two Town Hall, review), and its `Cache.db` holds 5 REST responses from today's session with the throwaway's content (no tokens). The 5a plan already lists "the disk image cache is not cleared at sign-out". Fix direction: clear `PersistentImageService`'s disk and memory caches and `URLCache.shared` in `AuthService.clearPerAccountLocalState()` (and therefore on account deletion). **Fixed in `5e560f7`.** `clearPerAccountLocalState()` now calls `PersistentImageService.shared.clearCache()` (disk and memory) and `URLCache.shared.removeAllCachedResponses()`, local only; built and the full suite passed, but no test drives that method and no sign-out was run on a device. Voice notes are cached in the temporary directory by `MessageAudioPlayer` and are still not cleared (not part of this fix).
- **G5. Sign-up logs the email address (pre-existing, low).** `AppLogger.auth.info("User signed up successfully: \(email)")` and the matching error line (`NaarsCars/Core/Services/AuthService.swift:249`, `:252`, both from before this phase). - Environment, not app: two pushes for the owner (`membership_update` at 20:48 UTC, `town_hall_post` at 21:28) were reported sent to APNs sandbox ("2 succeeded") but never reached the iPhone 16 simulator; other pushes to it did. On the conversations list at AX 5 the search field draws as an empty capsule (seen once, not investigated).

**CDN observation.** `town-hall-images/7DDF55E7-….jpg` by its public URL still answered **200 with `cf-cache-status: HIT`** (`cache-control: public, max-age=3600`, `last-modified` 2026-03-08) at 21:30 and again at 21:47 UTC, about five hours after the buckets became private; the same URL with a cache-busting query answers 400 from the origin.
