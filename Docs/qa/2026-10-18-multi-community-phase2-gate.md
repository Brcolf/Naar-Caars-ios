## PR Impact Summary

**Behaviour changes a reviewer must know about**

1. **The Profile badge counts `pending_members_total`** from `get_badge_counts` (applicants waiting in communities the person administers, plus default-community applicants for platform admins) instead of every unapproved profile. No client-side pending aggregation was added.
2. **Opening the Community tab, or switching its community, marks only that community's Town Hall rows read** (`clearCommunityBadge(visibleCommunityId:)`), not every Town Hall row.
3. **`.enterApp` while authenticated opens My communities** (a `user_approved` push for a further community) instead of doing nothing; it never relaunches an authenticated session.
4. **`pending_approval` with a `community_id` opens that community's Requests to join**; without one (platform admins' "Pending approvals") it opens the default community's Requests to join. The old `PendingUsersView` is no longer presented.
5. **`.needsApplication` shows community onboarding** (join with a code, ask a public community, create your own; name step for an "Apple User" profile) instead of the application form. The waiting screen lists the pending communities, offers Join another and Create your own, and relaunches only once and only when the account route no longer reads pending.

New member-facing surfaces: create a community (with the invite sheet: code, share, QR, admin options, live codes, revoke), join with a code or ask a public community, Requests to join (approve, decline; contact details only for platform admins), My communities (mute, leave with consequence counts, invite, report, requests to join), the owned-community limit request, the platform Communities list (archive, restore, public or private, limit decisions), the account-deletion warning for sole-owned communities, and the signed-out "I have an invite code" entry on Welcome (`PendingInviteStore`, cleared on redemption and on sign-out).

**Coordinator calls added** (all `forceFullRefreshAndWait` from ViewModels, none in `RefreshCoordinator.swift`): `(.badges, "communityMemberDecision")` after approve or decline; `(.dashboard, "leftCommunity")` after a leave; `(.dashboard, "joinedCommunity")` after an in-app create or instant join. No `invalidate` or `refreshIfNeeded` from a ViewModel. `RefreshCoordinator`, realtime, `MessageSendManager`, reactions, SwiftData models and mappers, `PushNotificationService` and the notification registry (33 types) are unchanged.

**High-blast-radius seams touched, and what breaks if a consumer is missed**

| Seam | Change | If a consumer were missed |
|---|---|---|
| `BadgeCountManager` / `BadgeCountManaging` | Profile badge from `pending_members_total`; per-community counts from `community_details`; `clearCommunityBadge(visibleCommunityId:)` | A caller still using the old unscoped clear marks every community's Town Hall read; a Profile badge computed elsewhere double-counts or shows every unapproved profile again. |
| `NavigationIntent` / `NavigationCoordinator` | `.pendingMembers(communityId)`, `.myCommunities`; `.enterApp` while authenticated → My communities | A `switch` without the new cases stops compiling; a consumer that maps `.pendingUsers` to the old screen shows platform admins a list that ignores communities. |
| `DeepLinkParser` / `NotificationNavigationRouter` / `AppDelegate` | `pending_approval` → `DeepLink.pendingMembers(communityId:)` / `NotificationIntent.openPendingMembers` | A path that drops `community_id` opens the default community's list for a community admin of another community (they then see the inline not-admin state). |
| `AppLaunchManager` | `readAccountRoute()`; onboarding as the `.needsApplication` root; guarded relaunch from onboarding and the waiting screen | A relaunch path that skips the guard loops on the waiting screen or relaunches twice. |
| `AuthService` | `PendingInviteStore().clear()` in `clearPerAccountLocalState()` | A saved code leaks to the next account on the device. |
| `CommunityContext` | `isPlatformAdmin`, `isAdmin(of:)`, `administeredPendingTotal`, `forgetMembership(_:)` | A left community or approved applicant stays on screen when the follow-up membership refresh fails. |
| `Constants` | Phase 2 limits and intervals (name, description and answer lengths, waiting-screen tick) | Client pre-validation drifts from the server's limits; the server still enforces them. |

**Database dependency.** The client calls the 19 Phase 0 step 5 RPCs above and reads `pending_members_total` / `community_details` from `get_badge_counts`. All are live (step 1). Refusals arrive as `{success:false, error, code}` and are shown as `CommunityRPCError.localizedMessage`, never the server's English text.

**Follow-ups to record**

- Community reports (`report_community`) are returned by `admin_get_reports`, but as target `user` with no member, no target id and no preview, because neither it nor `admin_moderate_content` has a case for `reported_community_id`. Admin → Reports labels such a row Community and says it cannot name the community yet (fix pass, `[P2-fix]`); it offers no Dismiss, because `admin_moderate_content` would log the dismissal in `content_moderation_events` with a null `target_id`, which that column refuses (NOT NULL, checked live 2026-10-18). A server change to both RPCs (a `community` target with the community's name as preview, and dismiss using `reported_community_id` as the target) is needed; until then the Communities list's "Reported" marker stays and these reports cannot be resolved from the app.
- A sole owner with other members cannot leave (`last_owner`) until Phase 3's transfer screen.
- Render findings 1–4 above (1 and 2 before release).
- Release prerequisite: the legal deliverable (Task 16) must be mirrored to the Notion pages the app opens before this client ships.

**App Store checklist** (spec §5). New system permission: no (the QR code is generated, never scanned). Stores data differently: yes (communities, memberships, invite codes, join answers, community reports; disclosed in the updated privacy policy, terms and FAQ). Account deletion: affected, still available on every route including onboarding and the waiting screen, with the A3 warning before deleting an account that closes communities. Reporting, blocking, moderation: new UGC surfaces (community names and descriptions, join answers) each have a report path (`report_community`); community admins never see who reported. Notification behaviour: routing of `pending_approval` and `user_approved` changes as above; no new type, no delivery change. Third-party SDK, entitlement, privacy-manifest change, payments: none.
