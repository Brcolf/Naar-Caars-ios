## PR Impact Summary (Phase 5a)

**What changes for people using the app: nothing visible.** No screen is added or redesigned, and no string key is added (75 keys become unused and stay in the catalog until an owner-approved cleanup). Only two things change behind the screens: where image and voice-note bytes are downloaded from, and which endpoint the ride-cost estimate calls for its place lookup.

1. **Removed screens and services**, all unreachable (table above): the legacy invite-code UI and service, the signup-method choice, the platform Pending Users screens, the application form, the debug view, the legacy `Log` enum and the dead Rides and Favors dashboards (21 files, every project reference gone, `PBXCHECK` clean).
2. **No client writes `profiles.heard_about`, `join_reason`, `application_complete` or `approved`, and none calls `admin_reject_pending_user`.** Answers reach `community_members` only through the community RPCs. The server's own copy of the answers into `profiles` (default community) remains until File B (D-9), because the installed build's admin screen reads it.
3. **Ride-cost place lookups go through two definer RPCs** (`get_geocoding_multiplier`, `put_geocoding_multiplier`; File A, live). They require an active account, validate the key, the coordinates and the multiplier range, and return or store only the multiplier. A cache row is fresh for 24 hours from its last write (`updated_at`). No placemark data is sent, and the 7 stored placemarks were cleared. A missing function (`PGRST202` / `42883`) turns the lookup off for the session; any other error leaves it on. The estimate itself still comes from the on-device rules. On device the RPCs were not reached: the estimate stalls in the address geocoding before the lookup (finding F1, which predates this phase).
4. **Images in `message-images`, `group-images`, `town-hall-images` and `review-images`, and voice notes in `audio-messages` (D-1, accepted), download through signed URLs** (`StorageURLSigner`: 1-hour lifetime, renewed 5 minutes before expiry, one request per object for concurrent resolves, at most 500 entries, in memory only, reset at sign-out). Downloads use `URLSession.signedStorageDownload` (ephemeral, no `URLCache`). The sign request itself goes through the shared Supabase client, whose session does use `URLCache.shared`: its response, which holds the token, is written to `Cache.db` and outlives sign-out (finding F2). The disk image cache and the audio temp files stay keyed by the stored URL. **What is stored does not change**: `messages.image_url` / `audio_url`, `conversations.group_image_url`, `town_hall_posts.image_url`, `reviews.image_url`, `SDMessage` and `SDTownHallPost` keep the public URL the upload returned (D-2), so the installed build keeps showing new media until File E. While the buckets are public, a signing failure falls back to the stored URL. A voice-note download that is not a 2xx answer is neither written nor cached (`61ef090`). Avatars stay public.
5. **Nothing in 5b is applied**: see "5b: NOT APPLIED" above. Files B-E wait for A5 point 2 (no pre-community build in use). Files D and E also wait until every build in use contains this client.

**Coordinator, realtime, send path.** `RefreshCoordinator`, `RealtimeManager`, `MessageSendManager`, `MessageSendWorker`, `MessagingRepository`, `BackgroundSyncActor`, `SDModels`, the mappers, `NavigationCoordinator`, `PushNotificationService`, `BadgeCountManager` and the notification registry are unchanged. No coordinator call is added. `MessagingSyncEngine` changes only in its private voice-note prefetch (above).
