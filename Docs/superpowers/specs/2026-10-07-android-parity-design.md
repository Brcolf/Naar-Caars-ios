## 1. Summary and recommendation

### 1.1 The recommendation in one paragraph

Build Android as a **one-to-one architectural twin** of the iOS app — same layers, same state machines, same invariants, same test-id vocabulary, same strings and tokens — in **Kotlin + Jetpack Compose**, with **no shared client code** (no Kotlin Multiplatform, no React Native or Flutter). Share three things instead, all of them checkable by machine: the **backend** (already shared: Postgres + RLS + SECURITY DEFINER RPCs + triggers + edge functions), a new **platform-neutral contract directory `shared/`** (a generated snapshot of the live schema, one JSON contract per RPC, JSON fixtures for push types, table rows, realtime *event sequences* and push *behaviour*, the notification-type and action registry, the behavioural constants with their semantics, the string catalog export, the design tokens, feature specs with numbered rules, Maestro scenarios, test ids with their accessibility labels, and a parity ledger), and a **seeded Supabase stack** built from a one-time schema dump of production — *not* from replaying `supabase/migrations/`, which this repo cannot do — with the production-pointing webhook function replaced before a single seeded row is inserted. The stack runs as throwaway containers on Linux CI for everything except the iOS scenario lane, which uses one hosted staging project built by the same script, because GitHub's Apple-silicon macOS runners cannot run Docker (§3.4). Agents work issue → spec → **contract PR first** → iOS PR + Android PR → mechanical ledger gate + advisory parity-reviewer agent → one combined PR, and releases are paired trains. A feature is `shipped` on a platform only when its scenarios passed on that platform at the PR head; from the moment a feature is shipped on both platforms, a change to one side must come with a change to the other or with a recorded divergence. Before any Android messaging code is written, the iOS send path and realtime manager get the tests they do not have today and the message insert is made idempotent, so the port copies one correct, tested path. The harness phases (0–3) are worth doing for the iOS-only project on their own; the Android port (phases 4–10) follows the iOS build order and ships messaging last, in two sub-phases.

### 1.2 Why this shape

- **The backend is the only layer both apps share, and it is the layer that has bitten the project repeatedly**: a live `should_notify_user` body that no migration file contains (notifications map §2 note, §16 #2), `badges.ts` reading a `total` key the RPC never returns (`supabase/functions/_shared/badges.ts:20-22`, **verified**), Town Hall pushes keyed `town_hall_post_id` while the client looks for `post_id` (`Core/Models/AppNotification.swift:191`, **verified**), two encodings for the same `uuid[]` parameter (backend map §5 #5). A second client written from the Swift code would copy every one of those; a second client written from a *tested* contract surfaces them. The harness is what makes the contract tested.
- **The hardened part of the iOS app is exactly what a shared core would replace.** `BackgroundSyncActor` is a `@ModelActor` (`Core/Storage/BackgroundSyncActor.swift:13`), `RefreshCoordinator.FreshnessState.refreshing` holds a Swift `Task` (`Core/Services/RefreshCoordinator.swift:28`), the durable send queue is SwiftData rows, `MessageSendWorker` is an `actor` with `PendingMessageInfo: Sendable` (`Core/Services/MessageSendWorker.swift:16`, `:306`), realtime callbacks are `@MainActor @Sendable` (`Core/Services/RealtimeManager.swift:19-21`), and the session lives in the Keychain (`Core/Services/SupabaseService.swift:105`) — all **(verified)**. None of that crosses a Kotlin/Swift bridge; a KMP core rewrites every one of those files on the live iOS app and buys iOS users nothing (§9).
- **For one owner plus agents, mirroring is the cheap operation — when there is something to mirror against.** Agents translate a Swift file into its Kotlin twin reliably when every Swift type has one named Kotlin home (§3.6) and both sides run the same JSON fixtures and the same Maestro flows. They are poor at diagnosing cross-language interop failures, which is the KMP failure mode. The review showed the limit of this argument: for the two riskiest files (`MessageSendManager` / `MessageSendWorker` and `RealtimeManager`) iOS has no test that exercises them, and the Kotlin SDK, Room and WorkManager do not behave like the Swift constructs with the same names. v2 therefore specifies the Android mechanism for each fragile row instead of naming a look-alike (§3.6), and writes the missing iOS tests first (§4 phase 3b).
- **The iOS app is live with 19 members; nothing they rely on may break, and almost nothing they see changes before Android ships.** Every phase below is additive on the backend, and the two visible changes are improvements shipped on their own (the icon badge shows the right number; a retried message can no longer appear twice). The iOS changes before Android exists are: test-only generated types and fixture tests, `accessibilityIdentifier` and label additions, a DEBUG-only places stub for hermetic scenarios, three small contract-bug fixes shipped as their own commits (§4 phase 0), and the pre-port hardening of phase 3b (characterisation tests, two extract-only seams for testing, and the idempotent message insert as its own fragile-system commit). The full list is in §3.10. v1's DEBUG-only backend override in `SupabaseService` is dropped: a test build is pointed at another backend by generating `Secrets.swift` at build time, which `ios-ci.yml` already does (`.github/workflows/ios-ci.yml:42-61`, **verified v2**), so no app code changes for it. The installed build (`CURRENT_PROJECT_VERSION = 11`, `NaarsCars/NaarsCars.xcodeproj/project.pbxproj:3046`, **verified**) keeps working through every phase.

### 1.4 What changed from v1

1. **The three fragile mappings are specified by mechanism.** Realtime: collectors are attached, unbounded, before the channel joins; the confirmation wait has a failure branch; every (re)join is followed by a hydrate (§3.6, §3.6.2 #1). Optimistic send: v1 (and CLAUDE.md) described `Manager → Worker → Service`; the code sends inline from the manager, once, and uses the worker as a recovery drain. Android mirrors what the code does, in process, and WorkManager is used only for the dead-process quick reply (§3.6, §3.6.2 #2). Repository: the messaging flows are repository-fed, never Room-observed (§3.6).
2. **The parity gate cannot be satisfied by a label.** Per-feature lockstep with a required diff on both sides, an ownership check for every source file, `shipped` derived from scenario results, a divergence file for platform-only fixes, a rule against silently moving due dates, numbered spec rules each tied to a proof, and a test-twin map (§2.2, §3.8).
3. **The cross-platform scenarios can actually run.** Each PAR scenario is two per-lane halves with the other party played by an API actor against the seeded stack and pushes injected through a bridge; the true two-device check is a dated manual pass that a release train requires (§2.3).
4. **Scenario sign-in needs no app change.** Flows start with a shared login subflow through the real Welcome and Login screens (§3.8).
5. **Shared fixtures cover behaviour, not dead shapes.** Realtime sequence fixtures, the six read-receipt echo cases, push behaviour fixtures (foreground suppression, badge throttle, targeted refresh) and edge cases for mute and membership replace the envelope-shape fixtures no client ever sees (§3.3).
6. **iOS is hardened before it is copied** (new phase 3b): characterisation tests for the send path and `RealtimeManager`, the idempotent insert, two extract-only test seams, and the owner's choice of small refactors (§4, §7 E7).
7. **The estimate is re-derived file by file** with the design's own rates and every §3.6.1 row mapped to a phase: about 190 agent-days (175–210) against v1's 127; messaging is 35–41 against 22 (§6).
8. **Owner time is restated as what the owner actually does** — hands-on steps and reading verification reports — and the merge rule is required checks only, because a one-collaborator repository cannot satisfy "one approving review" (§3.8, §6, §7 A10).
9. **Android work has no Mac lane.** Cloud sessions and Linux CI only; the calendar is redrawn along the real dependencies (§3.9, §6).
10. **Sign-in is specified end to end**: how a Google sign-in maps to an existing member or a new applicant, and the Apple Services ID, return URL, client secret and six-month rotation that Apple-over-web needs (§3.5).
11. **A release path exists**: Play account type and the closed-testing requirement on the critical path, Play App Signing, the upload key, who builds the bundle, the declarations checklist, and the Data Safety form before closed testing instead of at the end (§3.11, §4).
12. **The domain the design leaned on does not exist.** `naarscars.com` does not resolve (**verified v2**); acquiring a domain and static hosting is an owner step, and URL deep links stay push-only until it is done (§3.11, §7 D15).
13. **Android platform behaviour is designed for**: backup and restore of encrypted stores, push-token registration tied to the notification permission, background refresh after a push, foreground-bound timers, a debug-only cleartext rule, one application id, and a higher minimum SDK (§2.4, §3.6).
14. **Accessibility is a parity dimension**: every test id carries a label key checked on screen on both platforms, Compose accessibility checks run in CI, and a TalkBack pass is part of the phase gates (§3.12).
15. **Backend contract additions**: `register_push_token` (closes the one-token-two-accounts finding for Android from day one), per-token `last_used_at`, notification actions in the registry with one category map for both edge functions, RPC signatures with defaults in the snapshot, a generated Kotlin RPC layer and an iOS call-site key check (§3.3, §3.5).
16. **The two initiatives share one phase 0** and one fix per backend bug, and at most one backend-changing PR is open at a time (§3.4 #12, §4).
17. Decisions: eighteen new ones (A10, A11, B8–B10, C9–C11, D13–D19, E7–E9); A3, A4, A5, A8, A9, B1, B3, B4, B7, C5, C8, D2, D6, D8–D12 and E1 are revised (§7).

Two kinds of "user" matter here: members, who must see one product on two platforms, and the owner-plus-agents, who must see one workflow that cannot let the platforms drift.

### 2.2 Owner- and agent-facing rules (what the tooling enforces)

Definitions: a **feature** is a row in `shared/parity/ledger.yaml` that owns files on each platform; a **seam** is a cross-cutting file (`Constants.swift`, `NavigationCoordinator.swift`, a sync engine) listed in `shared/parity/seams.yaml` with its twin on the other platform; a **contract change** is any edit under `shared/contract/` and travels in its own PR with the migration or edge-function change that justifies it; a **scenario** is a Maestro flow under `shared/specs/scenarios/` that runs unchanged on both platforms; a **divergence** is a recorded reason why one change exists on one platform only (`shared/parity/divergences.yaml`); a **test id** is the `screen.control` string iOS already uses, mirrored as the Compose `testTag` with `testTagsAsResourceId` on the root. The iOS inventory is larger than v1 said: 129 distinct `.accessibilityIdentifier("…")` modifier strings (three interpolated), 18 more passed through an `accessibilityId:` parameter (`login.email`, `createRide.pickup`, …) and 12 assigned as properties in the UIKit messaging views (three interpolated) — about 159 ids, six of them patterns (**verified v2**).

1. **Contract before client.** No platform PR may reference an RPC, table, column, notification type, push key or storage bucket that is not in `shared/contract/`. `check-ledger.py` greps both codebases (multi-line aware) and fails on an unknown name.
2. **One registry.** `shared/contract/notification-types.json` is canonical. The Swift enum, `NotificationTypeRegistry`, `notificationTypes.ts`, the Kotlin enum, the `valid_notification_type` CHECK in the live snapshot, `NotificationFixtures` (until retired) and the `shared/contract/push/` directory must all match it. `scripts/validate-notification-types.sh` becomes a thin wrapper, not a second checker.
3. **Fixtures are JSON and shared.** Both test suites load the same files. The three Swift-literal fixture files are retired as each is covered by a JSON twin.
4. **Behaviour lives in the spec, platform details in the code.** A spec states numbered rules in platform-neutral terms; each rule has an id and names what proves it (a scenario, a fixture, a unit test, or a dated manual pass). UIKit-versus-Compose details are not in the spec.
5. **Ledger gate.** Until a feature is shipped on Android (port-after mode), a PR touching its iOS files needs a `parity_due` date that has not passed. **From the moment a feature is `shipped` on both platforms — per feature, not at a global date — a PR whose diff touches that feature's files on one platform must also touch its files on the other, or cite a divergence, or set the other platform to `in-progress` (which blocks the next train).** The same holds for a seam and its twin. After the `android-launch` milestone, `parity_due` is no longer accepted for any launch feature. `n/a` needs a reason string. The gate is always hard for `shared/contract/**` and `supabase/**`. The check posts what it decided (touched features and seams, and what satisfied the gate for each) as a PR comment.
6. **Proven before applied.** Every migration file is applied on the throwaway local stack in `contract-ci`, its pgTAP probes pass, and only then does an agent apply it to production through the MCP by the unchanged procedure (one function per call, header says APPLIED, committed in the same change). The header prose probes of the 2026-10 migrations become `shared/fixtures/probes/<migration>.sql` and run forever.
7. **Known gaps are declared, not hidden.** A fixture *or scenario* that encodes the real behaviour and fails on a platform is listed under `known_failures` with the audit-finding id and a due date (one train); the fix PR removes the entry. A past-due entry fails PRs that touch that feature, and shows in the weekly report; it never fails an unrelated PR.
8. **No production secret reaches PR-time CI.** PR workflows run with placeholders and the throwaway stack. The iOS scenario lane holds the staging project's credentials only (synthetic data, its own keys). The nightly live-contract job is the only job with a production credential, and it is read-only.
9. **Releases are trains.** A train is a tag that ships to TestFlight and Play testing together; it may not be cut while any feature in its milestone is `in-progress` on either platform, any migration header says NOT APPLIED, any `deferred-mirror` divergence is past due, or `releases.yaml` lacks the train's dated two-device pass (§2.3).
10. **Sanctioned deviations are a closed list** (§2.4). The parity reviewer approves a difference only if it is on the list, in the feature's spec `Platform notes`, or recorded as a divergence.
11. **A platform may be ahead**, recorded as a divergence of class `ahead` (v1's "parity exception") with the other platform's finding id (first entry: Android quick reply from a dead process, iOS `gap-1-notifications-push-routing-3`, `Docs/qa/2026-10-06-audit-findings.md:228`, **verified**).
12. **`shipped` is derived, not declared.** A feature's cell may become `shipped` on a platform only in a PR whose head has passing results on that platform for every scenario the feature lists and for its screen-inventory flow (§3.8). The same PR must list the platform's files.
13. **Every source file is owned.** Each file under `NaarsCars/{App,Core,Features,UI}` and `android/app/src/main/kotlin` matches a feature glob, is a seam, or is in `shared/parity/unowned-files.yaml` with a reason. A new file that matches nothing fails the check, so logic cannot sit outside the gate.
14. **One backend change at a time.** At most one open PR may touch `supabase/functions/**` or regenerate `schema.snapshot.json` (§3.4 #12).
15. **Dates do not move silently.** A PR that moves a `parity_due` or `due` later needs the `parity-extension` label and records `extended_from` and `extended_by_pr`; the ledger diff is posted on the PR in a fixed format.

### 2.3 Flow catalog

**Cross-platform scenarios (PAR set).** v1 wrote these as one flow with an Android user and an iOS user. That cannot run: Maestro drives one device per flow, each CI lane has its own backend, and the seeded stack never delivers a real push (the webhook override records the call instead, §3.4 #4). v2 therefore defines each PAR as **two halves, each run on each lane**: the device plays one party through the UI; the other party is an **API actor** — a script step that performs the same PostgREST write or RPC the other client would, under that seeded user's JWT; server state is asserted with a SQL probe; and a push is delivered by the **push bridge** (`shared/tools/push-bridge.py`: take the recorded `test.webhook_calls` row, run the real edge-function handler under deno with `fetch` captured, and inject the resulting APNs payload with `xcrun simctl push` or the FCM data map through a debug-only broadcast on Android). What a lane proves is "this client is correct against the shared contract from either side of the flow"; that both clients are, on the same backend, is what makes them interoperate. The one thing no lane can show — two real devices and real push transport — is a **dated two-device manual pass per train**, on production with two designated test accounts (§7 E8), recorded in `releases.yaml` and required by `release-train.yml`.

**Workflow scenarios (what the owner experiences):**

- **S1 — a new feature after Android is live** ("mute a whole community"). Owner files an issue from the template. `/spec` produces PR #1: the spec with numbered rules, two scenarios (each declaring which rules it proves), new test ids with label keys, `shared/contract/rpc/set_community_mute.json`, new arms in the affected `push/*.json`, the migration and its probe file. `contract-ci` boots the local stack, applies the migration, runs the probes, the RPC conformance cases and the breaking-change classifier, regenerates the Kotlin DTOs, the Kotlin RPC layer and the Swift test oracle and diffs them against what the agent committed. The owner reads the PR's verification report and merges; an agent applies the migration to production through the MCP. Two agents then work from the same spec in two worktrees (`claude/F-COMM-007-ios`, `claude/F-COMM-007-android`), each with a draft PR for its lane. `parity-merge.sh` merges both into `claude/F-COMM-007` and opens the one PR that may merge; that PR's scenario runs are what allow its ledger row to say `shipped` on both; the parity reviewer posts a per-rule checklist; the owner merges once.
- **S2 — an iOS-only fix in the UIKit messaging path** (a composer-inset bug). The PR touches `MessagesViewController.swift`, which belongs to `F-MSG-003`, shipped on both. The gate asks for one of three things. *Mirror:* the same behaviour is wrong on Android, so the PR (or its pair) changes the Android files too. *Divergence:* the fix is about UIKit mechanics Android does not have (the composer is not a keyboard accessory there), so the PR adds a `divergences.yaml` entry `{class: platform-only-fix, reason, verification: snapshot}` — no scenario is invented for a fix a UI flow cannot observe (Maestro's `assertVisible` passes for a partly covered bubble). *Deferred mirror:* Android needs the change but not today; the entry carries a due date and the next train waits for it. **The iOS fix is never blocked on Android being green**: scenario-only changes run the Android lane as an advisory check (§3.8).
- **S3 — a schema change old clients must survive** (the multi-community `community_id`). The contract PR carries the migration, the probes (as the legacy member: the old `rides` select still returns their rows; as `anon`: `guest_rides` still has every column the shipped decoder requires), and a **versioned** fixture: `tables/rides.row.v1.json` (what build 11 decodes) stays, `rides.row.v2.json` is added, and both platforms' decoding tests must accept both. The ledger marks the feature `in-progress` on both; no train ships until both are `shipped`.
- **S4 — drift detected.** Someone edits a function in the dashboard. The nightly job regenerates `schema.snapshot.json` from live and finds `should_notify_user`'s `prosrc` hash differs; it opens "Live contract drift: should_notify_user" with the diff. The next contract PR records the live body in a migration (`STATUS: RECORDED FROM LIVE`) or restores the committed one. This is already true today (notifications map §16 #2).
- **S5 — Android lags.** The weekly parity report shows the ~70 screens by status. A feature whose `parity_due` has passed turns the parity check red on PRs touching *that feature* only, so unrelated iOS work continues. Moving the date takes the `parity-extension` label and leaves a trail.
- **S6 — an App Store- or Play-sensitive change.** The spec template's Compliance block mirrors the CLAUDE.md checklist (new permission? data handling? deletion? moderation? notifications? SDK? privacy manifest / Data Safety?) and its Accessibility block lists the labels and roles of every new control. The parity reviewer refuses a platform PR whose spec blocks are unanswered, and a new SDK must appear in `shared/compliance/data-inventory.yaml` or `check-ledger.py` fails.
- **S7 — an agent marks a feature shipped too early.** The Android port PR for `F-REQ-001` flips `android: shipped`. The Android lane runs that feature's scenarios and its inventory flow because the ledger says they are now claimed; one fails; the `Parity gate` check is red and names the scenario. Nothing about the label alone can make it green.

### 3.3 The backend contract: generated and curated parts

**Generated (never hand-edited).**

- `schema.snapshot.json` is produced by `tools/snapshot-schema.sql`, a read-only query over `information_schema.columns`, `pg_constraint` (CHECK definitions verbatim, so `valid_notification_type` — last defined in `supabase/migrations/20260407202111_content_hidden_notification_type.sql:9-10`, **verified** — is captured), `pg_policies` (policy name, cmd, roles, `md5(qual)`, `md5(with_check)`), `pg_proc` ⋈ `pg_namespace` (identity arguments, **`pg_get_function_arguments(oid)` — names, types and defaults — and `pg_get_function_result(oid)`**, `prosecdef`, `proconfig`, `proacl`, `md5(prosrc)`), `pg_trigger`, `pg_views`. v1 recorded identity arguments only, which do not include defaults, so a dropped default would have passed. Functions are keyed by identity signature, so the two live `get_leaderboard` overloads (backend map B3) stay distinct. Against production it is run through the Supabase MCP `execute_sql` (a SELECT) or `psql` with the read-only role; the result is committed beside the migration that caused it. **CI rule:** a PR that changes `supabase/migrations/**` must change `schema.snapshot.json`, and the snapshot produced from the *local stack after applying the PR's migrations* must equal the committed one (the proof that baseline + newer migrations reproduce production). The nightly job proves committed == live.
- `storage.snapshot.json` (bucket rows from `storage.buckets`; policies on `storage.objects` from `pg_policies` with `schemaname = 'storage'`) and `cron.json` (`cron.job`) by the same route. Storage is in the snapshot because every bucket is `public = true` and the `message-images` INSERT policy has no conversation filter (backend map §1.6, §5 #12; `database/067_create_message_images_bucket.sql:10`, **verified** `public` on creation) — a hole private communities will have to close, and the probes must see it.
- Types: `supabase gen types --lang swift` and `--lang typescript` (both flags exist in CLI 2.67.1, **verified**) run in CI against the local stack (`--local`), so no production credential is needed at PR time. There is no official Kotlin generator; `gen-kotlin.py` emits `@Serializable data class` DTOs with `@SerialName("snake_case")` from the snapshot (nullable where the column is nullable; `kotlinx.datetime.Instant` for `timestamptz`, `LocalDate` for `date`, `String` for `time` because the iOS client treats `time` as `"HH:mm:ss"` text). The Swift output compiles into `NaarsCarsTests` only, consumed by one class, `ContractModelParityTests`, which asserts for each hand-written model that its `CodingKeys` ⊆ the generated row's columns and every non-optional `let` has a `NOT NULL` column — the "column missing from `guest_rides` breaks every guest" class of bug, caught at PR time. The app's hand-written models and the fragile mapper trio stay as they are.
- `Rpc.generated.kt` is emitted from `rpc/*.json`: one typed suspend function per RPC (`suspend fun getBadgeCounts(pIncludeDetails: Boolean = false, …)`) with the parameter names, the required/optional split and the `arg_encoding` baked in. Android call sites therefore cannot send a wrong or missing parameter name; this is the one place generated Kotlin pays for itself beyond DTOs (§7 B10). iOS passes string-keyed dictionaries nothing type-checks (`AuthService.swift:343`, `PushNotificationService.swift:686`), so `check-rpc-callsites.py` extracts the literal keys of every `.rpc("<name>", params: […])` site (multi-line aware; an allow-list names the few sites that build their parameters dynamically) and fails when a key is not in the contract's `args` or a required argument is absent. A renamed or newly required parameter is then a PR-time failure on both platforms instead of a runtime `PGRST202`.
- **Breaking-change classifier.** `snapshot-diff.py` does more than compare. Between the base snapshot and the PR's it classifies as **breaking**: a column removed or renamed, a type changed or nullability tightened on a table or view a client reads; a view missing a column its table gained (the `guest_rides` class of bug); an RPC argument removed or renamed, a default dropped, a key removed from a `response_schema`; a CHECK tightened; a grant revoked from `anon` or `authenticated`. A breaking change fails `contract-ci` unless the migration header carries `BREAKS-BUILDS-BEFORE: ios <n> android <m>` and `releases.yaml` marks those builds retired. A changed policy hash is always flagged, because a hash cannot tell loosening from tightening; the header line `POLICY-CHANGE-PROBED: <probe file>` clears it. Row fixtures get a superset test — every key and type in `tables/<t>.row.v<k>.json` is still present in `v<k+1>` — and `releases.yaml` records which row version each shipped build was tested against. This is what turns P12 and PAR-008 from an assertion into a check.

The `semantics` field exists because a name is not a behaviour. `badgeRefreshDebounce` is **`throttle-drop`**: a call made less than 5 s after the last *completed* refresh is dropped, nothing is scheduled in its place, and the first call in a quiet period runs at once (`BadgeCountManager.swift:88-90`, `:149`, **verified v2**). A Kotlin `Flow.debounce(5.seconds)` would do the opposite — wait for 5 s of silence and always emit the last call — and the two apps' badges would disagree during a burst. `badgeClearMessagesRefreshDebounce` (`:276-283`) is the separate **`debounce-trailing`** path. Each platform's `BadgeCountManagerTests` asserts both. If the owner would rather have a trailing refresh, iOS changes first, in its own fragile-system-7 commit. `enums.json` does the same for raw strings, including `CrashDomain` and `CrashErrorCode` so both platforms' crash dashboards filter on one vocabulary.

### 3.4 The seeded backend (the enabler, and the one piece with real risk)

**Where things run.** The development Mac has 8 GB of RAM, about 10 GiB free on its internal volume (the simulator set and DerivedData live on `/Volumes/DevSSD`), no JDK, Android SDK, Gradle, `adb`, deno, `psql` or Maestro, and a Docker Desktop install whose command-line links are broken (**panel**). Nothing in this plan installs or starts any of that on the Mac. The stack runs on Linux CI; the one hosted staging project serves the iOS scenario lane (#11). An agent about to install the Android SDK or start Docker on the Mac is in the wrong lane.

1. **Baseline.** The dump is taken once. v1 had the owner run `supabase db dump` on the Mac; that command runs `pg_dump` inside a container *(not re-checked)*, which the Mac cannot do today. v2's default is a `workflow_dispatch` job in `nightly-live-contract.yml` on `ubuntu-latest`: `pg_dump --schema-only --schema=public --no-owner` with a client of the server's major version, through the read-only role the nightly job needs anyway (`SUPABASE_READONLY_DB_URL`; the role needs `pg_read_all_data` so it can lock the tables it describes), uploading `schema.baseline.sql` as an artefact that an agent commits. No database password is typed on the Mac. *Not verified:* that a read-only role can take the dump on Supabase's managed Postgres. If it cannot, the fallback is v1's command on the Mac after Docker Desktop has been started once: `supabase db dump --linked -s public -f shared/fixtures/schema.baseline.sql` (CLI 2.67.1: `--linked` defaults to true, `-s` selects schemas, there is **no `--schema-only` flag**; **verified** from `supabase db dump --help`), which needs the database password (§7 B8). Either way, commit the file with a header naming the date and the newest migration file it includes. Nothing in it is secret: function bodies are already public in `supabase/migrations/`, and `vault.secrets` is not in the `public` schema. The dump also captures the live `should_notify_user` body that no migration file contains, which is reason enough to take it even without Android.
2. **Storage and cron.** The `storage` schema's own tables are created by the local stack image, so its DDL is not dumped; what the stack needs from storage is the six bucket rows and the policies on `storage.objects`, and those are regenerated as `storage.baseline.sql` from `storage.snapshot.json` (`tools/snapshot-storage.sql` over `storage.buckets` and `pg_policies`). `cron.json` records the two live jobs (`process-completion-reminders` every 5 min, `expire-past-open-requests` 03:15 UTC; backend map §1.5) and the overrides do **not** schedule them; a probe calls the functions directly. If the first implementation finds that `supabase db dump -s storage` produces a cleaner result than the catalog query, it may switch, but the snapshot diff must still cover bucket rows and objects policies.
3. **Local stack.** `tools/local-stack.sh`: `supabase start` on `ubuntu-latest` in CI — **never on the Mac** — then `psql` the baseline, then every `supabase/migrations/*.sql` whose header date is newer than the baseline (the `APPLIED <date>` header convention makes this parseable), then `storage.baseline.sql`, then `local-overrides.sql`, then `seed.sql`. Android scenarios, the probes, the RPC conformance run, the deno tests and the Android instrumented tests all use it.
4. **Overrides (mandatory in every non-production environment).** The live `invoke_edge_webhook()` reads the Vault secret and `net.http_post`s to `https://easlpsksbylyceqiqecq.supabase.co/functions/v1/<slug>` (`20261005_0002_webhook_shared_secret.sql:55-80`, **verified**). Applied unchanged on a local stack it would call **production** edge functions on every seeded message or notification insert (they would reject the secret, but the call must never leave the runner, and with a copied secret it would send real pushes to real members). `local-overrides.sql` replaces it with a function that inserts `{slug, payload}` into `test.webhook_calls`; the deno edge tests then feed those rows to the functions with `fetch` mocked. The override also stubs `net.http_post` behind a `test` schema function, creates `pgtap` (local only; never on production), and leaves `cron.job` empty. `probes/_invariants.sql` asserts the override is in place (`prosrc` of `invoke_edge_webhook` contains `test.webhook_calls`) and `local-stack.sh` refuses to seed if the assertion fails.

```sql
-- shared/fixtures/local-overrides.sql (sketch)
create schema if not exists test;
create table if not exists test.webhook_calls (id bigserial primary key, slug text, payload jsonb, created_at timestamptz default now());
create or replace function public.invoke_edge_webhook() returns trigger
language plpgsql security definer set search_path = '' as $$
begin
  insert into test.webhook_calls (slug, payload)
  values (tg_argv[0], jsonb_build_object('type', tg_op, 'table', tg_table_name, 'schema', tg_table_schema,
          'record', case when tg_op = 'DELETE' then null else to_jsonb(new) end,

```

5. **Seed.** Five `auth.users` with `crypt()`ed passwords (local only), their `profiles` (four approved, one pending; `dave` is admin), rides/favors/posts/conversations with fixed UUIDs the fixtures reference, and `push_tokens` rows with fake tokens on both platforms. JWTs for probes and the conformance runner are minted from the local JWT secret (`supabase status -o json`).
6. **Probes.** `probes/<migration>.sql` are the 2026-10 migration headers' prose probes turned into pgTAP assertions (the style the migrations already describe: `begin; set local role authenticated; set local request.jwt.claims = …; … rollback;`), e.g. `throws_ok($$ update public.rides set notes = 'x' … $$, '42501')` for `guard_request_client_update`, which really raises `42501` (`20261006_0001`). `run-probes.sh` executes them with `pg_prove`. The twenty-odd 2026-10 migrations are back-filled first (guard trigger, reviews insert, invite-code guard, guest views, address cut-over, participants policy, message RPC gates, `submit_report` dedupe, account deletion end to end, admin reject null-safe, helpers answer only for the caller).
7. **RPC conformance.** `rpc-conformance.py` runs every `cases[]` entry against local PostgREST (`http://127.0.0.1:54321/rest/v1/rpc/<name>`) with the seeded user's JWT, checks status and JSON Schema, replays the exact `arg_encoding`, and re-seeds between mutating groups (v1 wrote `supabase db reset` here, which replays the migration history this repository cannot replay).
8. **Edge functions.** `deno test` under `supabase/functions/` (none exist today, **verified**) with `fetch` mocked: for each `edge/<slug>.<case>.json`, call the handler with the webhook row and assert the APNs body and, after phase 4, the FCM body equal `push/<type>.json` minus dynamic fields, or assert the expected skip (muted, recently seen, blocked, left the conversation, banned). This is where `badges.ts` reading a key the RPC never returned would have failed on day one. The same harness is what the **push bridge** (§2.3) runs to turn a recorded webhook call into a payload a simulator or emulator can receive.
9. **Snapshot as a CI artefact.** `contract-ci / backend` regenerates `schema.snapshot.json` from the local stack after applying the PR's migrations and diffs it against the committed file; on mismatch the job fails **and uploads the regenerated file** so the agent copies it into the PR (`gh run download`). The Mac never needs Docker to keep the snapshot honest.
10. **Clients against the stack — no app code needed.** v1 added a DEBUG-only override in `SupabaseService` that read two environment variables. v2 drops it. iOS: the lane writes `Secrets.swift` for the target backend at build time, exactly as `ios-ci.yml` already does from `SUPABASE_URL` / `SUPABASE_ANON_KEY` (`.github/workflows/ios-ci.yml:42-61`, **verified v2**); the app is unchanged, and staging is HTTPS so App Transport Security is not involved. The session-gated tests that today write to production when a user is signed in (`RideServiceTests`, `FavorServiceTests`, `TownHallServiceTests`, …; tooling map §3.4) gain a precondition in test code only: run when the configured backend is not the production project, otherwise `XCTSkip("refuses to write to production")`. The nightly iOS lane runs the unit suite once after the login flow, so those 33 cases run their real assertions, against synthetic data, for the first time (that the test host picks up the session the flow left in the simulator's Keychain is to be confirmed in phase 2). Android: `BuildConfig.SUPABASE_URL` from Gradle properties / instrumentation arguments (`http://10.0.2.2:54321` on the emulator). Android blocks cleartext HTTP by default, so the **debug source set** carries a `network_security_config.xml` permitting cleartext to `10.0.2.2` and `127.0.0.1` only, and a lint check fails a release manifest that permits any.
11. **The hosted staging project (iOS scenario lane only).** GitHub's Apple-silicon macOS runners are themselves virtual machines without nested virtualisation, so the Docker VM cannot start on them (`actions/runner-images#9460`, checked 2026-10-07; re-check when phase 3 starts, since newer runner hardware may lift this). v1's "local stack on the runner" for `scenarios-ios.yml` could not have worked, and the Mac cannot host the stack either. The iOS scenario lane therefore runs against one hosted Supabase project, `naars-cars-staging`, that is **built and reset only by `tools/staging-reset.sh`**: recreate `public` and `test`, apply the baseline, the newer migrations including the PR's, `storage.baseline.sql`, `local-overrides.sql`, `seed.sql`, then assert `_invariants.sql`. The webhook override is the same one — calls are recorded in `test.webhook_calls` and nothing is sent — so staging needs no APNs or FCM credentials and cannot push to a real member; the push bridge injects instead. It has its own keys; production's Vault secret is never copied to it. Because the repository is public and a hosted project is reachable from the internet, the seeded users' passwords on staging are generated at each reset and handed to the lane, not the committed ones the local stack uses. The lane serialises on a `concurrency: staging` group. `STAGING_DB_URL` and the staging publishable key are Actions secrets read only by `scenarios-ios.yml`, which never runs for a fork. A free-plan project is enough and the nightly run keeps it from being paused (§7 B4).
12. **One backend change at a time.** `schema.snapshot.json` and each edge function's source are whole-file artefacts: two open PRs that each regenerate the snapshot, or two branches that each deploy `send-notification` through the MCP (which has no notion of branches), overwrite one another. `check-ledger.py --backend-lock` in `contract-ci / static` lists open PRs through the GitHub API and fails a PR that touches `supabase/functions/**`, `supabase/migrations/**` or the snapshot while an older open PR does. An edge function is deployed only from `main`, after its PR has merged. This matters most while this initiative and multi-community run side by side (§7 A11).

```sql

-- Live columns: id, user_id, device_id, token, platform, created_at, updated_at, last_used_at

-- One device, one account; one token, one account. Closes gap-3-session-transitions-local-st-1
-- for every client that registers through it.
create or replace function public.register_push_token(p_device_id text, p_token text, p_platform text)
returns void language plpgsql security definer set search_path = '' as $$
declare v_uid uuid := (select auth.uid());
begin
  if v_uid is null then raise exception 'not authenticated' using errcode = '42501'; end if;
  if p_platform not in ('ios', 'android') then raise exception 'unknown platform' using errcode = '22023'; end if;
  delete from public.push_tokens
   where user_id <> v_uid and (device_id = p_device_id or token = p_token);
  insert into public.push_tokens (user_id, device_id, token, platform)
  values (v_uid, p_device_id, p_token, p_platform)
  on conflict (user_id, device_id) do update set token = excluded.token, platform = excluded.platform;
end $$;
revoke all on function public.register_push_token(text, text, text) from public, anon;
grant execute on function public.register_push_token(text, text, text) to authenticated;
```

The function can remove another account's row only for a caller who presents that row's device id or token, both of which are unguessable and held only by the device itself. It is a sketch to be proven on the throwaway stack; its probe asserts that a second account registering the same device id leaves exactly one row. Android registers through it from its first build. iOS keeps its select-then-update-or-insert until it adopts the RPC in its own commit (§7 B9).

**The `push_tokens` contract for an Android row** (written into `tables/push_tokens.row.v1.json` and the push spec; v1 left it open):

| Field / event | iOS today | Android |
|---|---|---|
| `device_id` | a UUID in the Keychain that survives reinstall (`Core/Utilities/DeviceIdentifier.swift:12`) | a per-install UUID in the encrypted DataStore; never `ANDROID_ID`; a reinstall gets a new one (§2.4) |
| `platform` | `'ios'` | `'android'` |
| `token` | the APNs device token | the current FCM registration token |
| Registration | after sign-in, sign-up and session restore, whatever the authorization status (`PushNotificationService.swift:365-376`, **verified v2**) | after sign-in, sign-up and session restore **when notifications are enabled for the app**; on each foreground the app re-checks and deletes the row if they have been turned off, or registers if they have been turned on |
| Token rotation | APNs re-delivers the token at launch | `onNewToken` while signed in and enabled → `register_push_token` (updates the `(user_id, device_id)` row) |
| Sign-out | delete by `(device_id, user_id)` before `auth.signOut()` | the same, in the same order |
| Server-side invalidation | APNs 410 → delete | FCM `UNREGISTERED` / 404 → delete |

*Apple over web OAuth.* The iOS app signs in natively with an ID token (`AuthService+AppleSignIn.swift:101`, `:154`), which needs only the bundle id in the provider's client-id list. Owner steps, about an hour:

1. In the Apple Developer account, create (or confirm) a **Services ID** in the same team, with Sign in with Apple enabled and `com.NaarsCars` as its primary App ID. Apple's user identifier is scoped to the team, so a Services ID in the same team yields the same `sub` and Supabase finds the member's existing identity; one created under another team would not.
2. Register `https://<project-ref>.supabase.co/auth/v1/callback` as the Services ID's Return URL and the project host as its domain.
3. Generate the **client secret** (a JWT signed with the `.p8` key; Apple caps its life at six months) and enter it in the Supabase Apple provider.
4. **Add** the Services ID to the provider's Client IDs and **keep `com.NaarsCars` in the list** — removing it breaks native sign-in on the installed iOS app with an "unacceptable audience" error, on an App Store 4.8 surface.
5. Add `com.naarscars://auth` to Supabase's redirect allow-list; the Android manifest declares the matching intent filter.
6. Record the secret's expiry in `releases.yaml`. The nightly job fails from 30 days before that date until it is renewed. Nothing can probe an expired secret from outside — it only fails at the token exchange — so the recorded date is the control. **This is a recurring obligation that exists only because of Android**, and its lapse silently breaks Apple sign-in on Android for the members who have no other method (§7 D2).

Linking Apple from Android uses `linkIdentity(Apple)` through the same web flow; `link_apple_identity` and `unlink_apple_identity` stay iOS-only in their `clients` field. Acceptance (phase 5 checklist): an account whose Apple identity was created natively on iOS signs in through the web flow on the Android phone and lands on the **same** `profiles` row. A web-OAuth Apple sign-in does not hand the client an authorization code, so `revoke-apple-token` (which requires one, `index.ts:59-67`) cannot run from Android: an Apple-linked account deleted from Android is deleted (`delete_user_account` runs first on Android), but Apple's grant stays until the person removes it under their Apple ID settings, and the Android deletion confirmation says so.

**Recorded, not done here:** the live `should_notify_user` body is exported into a migration marked `STATUS: RECORDED FROM LIVE` in phase 0 so no later `CREATE OR REPLACE` from a committed file can drop the `content_reported` / `content_hidden` arms (notifications map §16 #2); `get_or_create_request_conversation` references columns that do not exist (backend map §5 #1) and goes in `rpc/_excluded.json` with "broken; drop"; the `action: completion_response` path in `send-notification` (`index.ts:187-215`) calls an `auth.uid()`-gated RPC with the service client and can never succeed (notifications map §16 #8), so it is recorded as `edge/send-notification.completion-response.json` with `status: dead, not ported` and Android answers a completion reminder through the RPC directly, as iOS does.

#### 3.6.2 The CLAUDE.md fragile-system invariants, restated as things Android enforces

1. **Realtime pipeline.** The order is unchanged — `event → RealtimePayloadAdapter → MessagingSyncEngine.handleIncomingMessage → MessagingRepository.upsertMessageDetailed (under the Mutex) → repository flows → ViewModel → UI` — and nothing else touches `MessageEntity` rows for the active conversation (`excludeMessagesForConversation` ported). What v1 left to a look-alike is specified:
   - **A fresh channel per subscription.** `postgresChangeFlow` cannot be created on a joined channel, and cancelling a collector removes its join configuration, so iOS's `unsubscribe(removeConfig: false)` → resubscribe path (`RealtimeManager.swift:300-312`) has no equivalent. Unsubscribing removes the channel; resubscribing builds the channel, the flows and the collectors again.
   - **The collector is the buffer.** For each of the three change streams: `channel.postgresChangeFlow<…>(…).buffer(Channel.UNLIMITED)`, with `buffer` applied directly to the SDK's flow (adjacent to it, it makes the flow's own channel unbounded; an operator in between would leave the 64-slot default that drops silently), launched in `realtimeScope = CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)`, which the manager owns. Never `flowOn`. This plays the part of the Swift stream that queues from creation.
   - **Join after attach.** `subscribe()` is called only once every collector is attached. The SDK exposes no "callback registered" signal, so the manager makes the order deterministic itself: each collector is launched undispatched on the main-immediate scope and the manager yields once before it calls `subscribe()`. A `RealtimeManagerTest` with a fake channel asserts that no join is sent before all three callbacks are registered; an instrumented test against the local stack's Realtime writes 200 updates in one transaction while the collector is deliberately slow and asserts none is lost. The `supabase-kt` version is pinned and both tests run on every bump, because all of this rests on SDK internals read from its source, not on a documented contract.
   - **A bounded wait with a failure branch.** `withTimeoutOrNull(subscriptionConfirmationTimeout) { channel.status.first { it == SUBSCRIBED } }`, never `blockUntilSubscribed = true`. On timeout the engine hydrates anyway, as iOS does (`MessagingSyncEngine.swift:244-262`). A status collector that lives as long as the subscription then does two things: on **every** transition to `SUBSCRIBED` — the late first join and every rejoin after a reconnect — it runs `hydrateConversation`; and when the status falls back to `UNSUBSCRIBED` while the subscription is still wanted (the SDK gave up after its attempts) it does what iOS does on a thrown subscribe: cancel the collectors, remove the channel, log, and leave the next `subscribeToConversation` a clean start.
   - **Known gap, both platforms:** the hydrate fetches messages, not reactions (`MessageService.swift:186-187`), so a reaction event lost in the join window is healed only when the thread is reopened. Recorded as a shared finding, not fixed here.
2. **Optimistic send.** Only `MessageSendManager.sendMessage / sendAudioMessage / sendLocationMessage / retryMessage` create `status = 'sending'` rows, and each sends inline once. Send status has exactly two writers: `MessageSendManager` (success → sent; error → failed) and `MessageSendWorker`'s drain (success → sent; attempts exhausted → failed). `isPending` and `localAttachmentPath` are cleared only on server acknowledgement; media uploads complete before the insert. Every insert carries the pending row's id; a `23505` counts as an acknowledgement only when a follow-up select by that id returns a row with the caller's `from_id` and the same conversation, otherwise the row is marked failed. Konsist: only those two classes call `MessageService.send*`; nothing under `feature.*` references WorkManager.
3. **Reactions:** `Message.setIndividualReactions()` is the only mutator; `reactions` is a derived `val` (Kotlin can enforce what a Swift struct chose a setter for); the badge composable sits above the bubble. Konsist forbids other writers.
4. **Notification routing:** `data map → DeepLinkParser → DeepLink → NavigationCoordinator.applyPushDeepLink → pendingIntent → consumer`. No composable, service or receiver navigates directly; the messaging service and the action receiver may post a notification, start the expedited refresh and call the action's `server_call`, nothing else.
5. **Auth and launch:** `initializing → checkingAuth → ready(authState)`; `AppState` mirrors `AuthService` through one flow; sign-out phases 1–4 in the same order (token delete first); a session store that cannot be read is a signed-out launch, never a crash and never the "clear local data" dialog (that dialog stays for a Room open failure, as `NaarsCarsApp.swift:93-99`).
6. **Sync engine lifecycle:** `setup → startSync (no fetch) → performFullSync / performTargetedSync (coordinator only) → teardown (session work only)`; engines keep their DB handle across sign-out; refresh jobs live in the coordinator's scope and "join in flight, never cancel except `reset()`" is literal. Konsist: no `SyncEngine` symbol in `feature.*`; ViewModels may reference only `RefreshCoordinator.forceFullRefreshAndWait`; `cancel()` on a refresh job appears only in `reset()`.
7. **Badges:** push-triggered; a refresh requested less than 5 s after the last completed one is **dropped, not deferred** (`throttle-drop`, §3.3); the separate trailing refresh after clearing a conversation; the 5-minute safety poll while in the foreground; `get_badge_counts` authoritative; stale values with a flag on failure. Konsist: only `RefreshCoordinator` calls `BadgeCountManager.refreshAllBadges`.
8. **Room schema:** additive only; every change ships an `@AutoMigration` or hand-written `Migration` plus the exported schema JSON; `MigrationTestHelper` opens the previous schema and migrates.
9. **Observation:** repository subscriptions start in an idempotent `start()`, never in `init` (the 2026-10-05 render-loop lesson).
10. **Tests travel with the code, and where iOS has none they are written on iOS first.** The iOS classes that exist are ported case for case onto the shared fixtures, and `tests.yaml` records each pair: `RefreshCoordinatorTests` (10 cases), `MessagingSyncEngineTests` (6, the read-receipt echo), `BackgroundSyncActorConversationSyncTests` (3, the prune rule), `MessagePaginationManagerTests` (2), `AnyCodableEncodingTests` (4), `DeepLinkParserTests` (12), `NavigationCoordinatorRoutingTests` (14), `AppLaunchManagerTests` (2), `BadgeCountManagerTests` (6), `ConversationsListViewModelTests` and `ConversationDetailViewModelLifecycleTests` (the subscribe-in-`start()` cases), `ConversationDetailViewModelRealtimeTests` (counts confirmed by the panel; the review had two of them wrong and v1 one). That list does not touch the two riskiest files: nothing in the iOS suite references `MessageSendManager` or `MessageSendWorker`, and `RealtimeManagerTests` is one case that asserts `true` (**verified v2**). So phase 3b writes `MessageSendCharacterisationTests` and `RealtimeManagerLifecycleTests` on iOS before Android messaging starts, and those are what phase 8a ports.
11. **Timers and lifecycle.** A repeating timer exists only between `ON_START` and `ON_STOP` of `ProcessLifecycleOwner`; one class, `core/lifecycle/ForegroundTimers`, owns them, and Konsist forbids a `delay` loop, `Timer` or `fixedRateTimer` anywhere else. The 5 s grace period and the 30 s background unsubscribe are one-shot delays that begin when the conversation or the app leaves the foreground; because a cached process may be frozen before they fire, `ON_START` re-evaluates both from the monotonic time recorded at stop and tears down and resubscribes (with a hydrate) when the delay has elapsed.
12. **Stores and backup.** Nothing is backed up or transferred. Every read of the encrypted store goes through one wrapper that, on a decryption failure, deletes that store and reports "no value". An instrumented test restores a store encrypted with a different key and asserts the app lands on Welcome.
13. **Push token and permission.** A `push_tokens` row for this device exists only while the user is signed in **and** notifications are enabled for the app; the check runs at sign-in, on `onNewToken` and on every `ON_START`. With notifications off, a data message that still arrives runs its refresh and posts nothing.
14. **Accessibility semantics.** Every control that carries a `testTag` also carries the role and the `contentDescription` (or text) named by its `label_key` in `test-ids.json`; decorative images are cleared from semantics; touch targets are at least 48 dp (§3.12).

### 3.7 Strings and design tokens

**Strings.** `NaarsCars/Resources/Localizable.xcstrings` stays the source of truth (Xcode's catalog editor and `SWIFT_EMIT_LOC_STRINGS` operate on it; the pre-commit hook guards it). `gen-strings.py` reads the JSON (`strings.<key>.localizations.<lang>.stringUnit.value`), writes `shared/strings/android/values*/strings.xml` and `keys.json`, converting `%@` → `%s`, `%lld` / `%d` → `%d`, positional `%1$s` when a value holds two or more specifiers (**verified**: 125 keys carry at least one specifier, **27** carry two or more), and mapping the **210** non-identifier keys (**verified**) through `aliases.json`, generated once and frozen; `check-strings.py` fails a PR that adds a new key that is not `[a-z][a-z0-9_]*`, which also closes the gap in the existing hook that only sees snake_case keys. No plurals exist, so no `<plurals>` mapping; the `_one` / `_other` convention is documented for both platforms. CI regenerates and `git diff --exit-code`s, and compares the `strings.xml` key set with the keys referenced in `android/**/*.kt` so an Android screen cannot ship with a key iOS does not have (a key is born only in the catalog). The four `Info.plist` permission strings that live in `project.pbxproj` in English only (client-ui map §6) get catalog keys on the Android side and are a known iOS-only gap. Five properties of the real catalog that v1's exporter would have tripped on (**verified v2** by parsing the file: 1,586 keys, six languages):

- **24 keys have no English value.** iOS shows the key text for them (CLAUDE.md QA notes). The exporter emits the key text too, so both apps show the same thing, and `check-strings.py` fails any *new* key without an English value.
- **Android resource escaping is more than XML escaping.** 115 English values contain an apostrophe, which the Android resource compiler rejects unescaped. The exporter escapes `'` and `"`, a leading `@` or `?`, newlines, a literal `%` in a value that also has specifiers, and `&` `<` `>`; a round-trip test loads every generated string through Android's resource parser in a Robolectric test and compares it with the catalog value.
- **1,213 keys are marked `stale`** in the catalog, because Xcode's extraction cannot see `"key".localized`. The catalog therefore cannot say which keys are in use, and P10's "same 1,586 keys" would carry dead keys to Android for good. `gen-strings.py --unused` greps both codebases for `"<key>".localized` and `R.string.<name>` and reports keys neither references; the dead ones are retired in phase 1 in their own commit (the pre-commit hook exists to make key removal deliberate, which this is).
- **The in-app language picker** writes `AppleLanguages` on iOS (`Core/Utilities/LocalizationManager.swift:57-69`). Its Android twin is `AppCompatDelegate.setApplicationLocales` plus `android:localeConfig` pointing at a generated `locales_config.xml`, so the system's per-app language screen offers the same six.
- **Chinese folders are named by script**, `values-b+zh+Hans` and `values-b+zh+Hant`, matching the catalog's `zh-Hans` / `zh-Hant`. v1's `zh-rCN` / `zh-rTW` would have left a Traditional-Chinese reader in Hong Kong on the English fallback.

The Play store listing (title and descriptions per locale) is an owner item in phase 9; it is not in the catalog.

**Tokens.** `shared/design/tokens.json` (moved; symlink kept so the README's links work) generates `android/.../ui/theme/Theme.generated.kt` and **checks** Swift: `gen-tokens.py --check` parses the hex literals in `NaarsCars/UI/Styles/ColorTheme.swift`, the sizes in `Typography.swift` and `Constants.Spacing` / `Radius`, and fails when they differ. Generating Swift was rejected: the 2026-10-06 uniformity pass just settled 107 view files. v1 stopped at "a Material 3 scheme generated from `tokens.json`". That is not implementable as written: the file holds 15 hex color pairs and 7 iOS system aliases with no hex at all, a Material scheme has about three dozen roles, the type styles are SF Pro at Dynamic Type "Large", elevation is an iOS shadow, and motion is a SwiftUI spring (**verified v2**). ### 3.8 Specs, scenarios, test ids, ledger and the CI matrix

**Spec template** (`shared/specs/TEMPLATE.md`): id, title, status, owner-decision links; Scope; **numbered platform-neutral Behaviour rules in YAML front matter**, each citing the constant or RPC and naming its proof; Screens and test ids; Contract references; Scenarios; **Accessibility block** (§3.12); Compliance block (CLAUDE.md checklist plus the Android analogue per item: Data Safety entry instead of the privacy manifest, Play account deletion, the permission matrix of §3.11); Fragile systems touched; Platform notes (`ios:` / `android:`); Open decisions.

Three things differ from v1's example. **Sign-in is a subflow, not a hook.** v1's flows began with `launchApp: { arguments: { NAARS_TEST_USER: "alice" } }` and a comment that a DEBUG test mode would sign the user in, while the same document promised the auth and launch path would not be touched; the app reads no launch arguments today (**panel**), so the iOS lane had no way to sign in. `_login.yaml` taps `welcome.emailLogin`, fills `login.email` and `login.password` with the seeded user's credentials, taps `login.submit` and waits for the dashboard — ids that exist today (`Features/Authentication/Views/LoginView.swift:61`, `:78`, **verified v2**) and the same route the existing XCUITests take. It needs no app change and exercises sign-in on every run. **The flow ends on a server probe and asserts the thing it created**, so tagged placeholders reachable in order cannot pass it. **Places are stubbed.** `createRide.pickup` and `createRide.destination` are autocomplete fields backed by `MKLocalSearchCompleter` on iOS and Google Places on Android, both live network services with different answers; a scenario that asserted a suggestion, the route map or the estimate would measure the network. A DEBUG-only `PlacesProvider` stub on both platforms, switched on by the `NAARS_PLACES_STUB` launch argument, serves `shared/fixtures/places.json`. On iOS that is a few DEBUG-only lines in `LocationService` (not a fragile system), its own commit in phase 3; `check-ledger.py` refuses a scenario that touches those ids without `requires: [places-stub]`.

The same file runs on the iOS simulator and the Android emulator; `id:` maps to `accessibilityIdentifier` and to `resource-id` (Compose: `Modifier.semantics { testTagsAsResourceId = true }` on the root, `Modifier.testTag("createRide.post")` on controls). Light/dark/large text are not scenario steps; the lane wraps each run three times (`xcrun simctl ui booted appearance dark` / `content_size accessibility-extra-extra-extra-large`; `adb shell cmd uimode night yes` / `adb shell settings put system font_scale 2.0`).

**Test ids.** `shared/ids/test-ids.json` is generated from the existing ids in all three forms iOS uses (the modifier, the `accessibilityId:` parameter and the UIKit property; about 159, §2.2), then hand-extended during the back-fill. Each entry carries `screen`, `kind`, `role` and `label_key`; the six interpolated ids are entered as patterns with their values enumerated where the set is closed (`claim.button.{state}`, `requests.filter.{id}`, `overlay.action.{name}`) or typed where it is not (`userSearch.row.{uuid}`, `overlay.reaction.{emoji}`, `details.reaction.{emoji}`). `check-ids.py` asserts that every id appears in the iOS source when its feature is `ios: shipped` (same for Android) and that no source file uses an id not in the file. That is a presence-in-source check and v2 does not rely on it alone: `gen-inventory.py` emits one flow per screen that opens it with seeded state and asserts every id of the screen is **visible, with its label** (§3.12), and those flows are part of what a `shipped` cell needs. UI tests that select by English label (`"Create Ride"`, `"Sign Out"`; tooling map §4) are converted to ids as part of the sweep, and the hard-coded credentials in `NaarsCars/NaarsCarsUITests/NaarsCarsUITests.swift` (a test account plus personal-domain addresses — **verified** present — in a public repository) are removed in phase 0 and those passwords rotated.

Divergence classes: `platform-only-fix`, `platform-only-ui`, `platform-only-structure` (none needs a date), `deferred-mirror` (needs `due`), and `ahead` (needs the other platform's finding id; this replaces v1's `exceptions:` list, and is written "android-ahead" or "ios-ahead" elsewhere in this document). `verification` may be `unit`, `snapshot`, `manual` or `scenario:<id>`; a fragile-system fix no UI flow can observe uses one of the first three instead of an invented scenario. The port agent's prompt reads this file first, and the parity reviewer lists every divergence it relied on.

`check-ledger.py`, in order:

1. **Schema and paths.** Every `spec`, `scenario` and `files` glob resolves; a platform cell that is `in-progress` or `shipped` must list files; a feature with screens must list at least one scenario, and a feature without any (pure infrastructure) is marked `no-ui` with a reason and proves each rule by fixture or unit test — an empty scenario list can never satisfy the gate.
2. **Ownership.** Every source file under `NaarsCars/{App,Core,Features,UI}` and `android/app/src/main/kotlin` matches a feature glob, is a seam, or is in `unowned-files.yaml`. Without this a PR that edits `Core/Services/MessageService.swift` or puts new logic in `Core/` touched no feature and the gate said nothing: there are 156 Swift files under `App/` and `Core/` against 142 under `Features/` (**panel**).
3. **Contract coverage.** Every RPC, table and push-type name extracted from both codebases belongs to a feature and has a contract file; every contract file is referenced.
4. **Test ids, labels and string keys.**
5. **Rules.** Each rule of a feature shipped on a platform has a proof on that platform.
6. **Test twins.** For a feature shipped on both, each class in `tests.yaml` exists on both sides; the weekly report prints the XCTest-method against `@Test`-method counts, and a twin with fewer cases than its source keeps the feature `in-progress`.
7. **The parity gate, per PR.** Touched set = features whose files intersect the diff, plus touched seams.
   - Shipped on both: a diff on one platform's files needs a diff on the other's, or a divergence entry added in this PR for that feature and platform, or the other cell set to `in-progress`.
   - Seam touched: the twin is touched or a divergence is cited.
   - Android `missing` or `in-progress`: a `parity_due` in the future while the milestone gate is `port-after`.
   - A cell that becomes `shipped`: checked by the `Parity gate` job against the scenario results (below).
   - A `parity_due` or `due` moved later: needs the `parity-extension` label and the `extended_from` / `extended_by_pr` fields.
   - Past-due `known_failures`, `parity_due` and `deferred-mirror` entries fail only PRs whose touched set includes their feature.
8. **Compliance.** Every dependency in `android/app/build.gradle.kts` and the iOS package list has a row in `data-inventory.yaml`.
9. **Backend lock** (§3.4 #12).
10. **Report.** A PR comment in a fixed format: the touched features and seams, what satisfied the gate for each, and the ledger diff (statuses, dates, divergences).

`releases.yaml` records trains (tag, iOS `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION`, Android `versionName` / `versionCode`, features, migrations that must be APPLIED, the row-fixture version each build was tested against, the dated two-device pass `{date, devices, scenarios}`, the dated manual accessibility passes, store acceptance dates) and the expiry of the Apple web client secret.

### 3.9 Agent workflow, manuals and hooks

**Issue → spec → contract PR.** `.github/ISSUE_TEMPLATE/feature.yml` asks for the behaviour in a paragraph, platforms (both / iOS only / Android only with reason), expected contract changes, fragile systems, compliance flags. `/spec` (new command) runs the existing brainstorming skill, writes the spec, scenarios, test ids, contract files, migration and probe, updates the ledger (`in-progress` on both or `n/a`), and opens the **contract PR** (`claude/<F-id>-contract`). It stops there: the contract PR merges before any client work, and the migration is applied to production by the unchanged MCP procedure, now preceded by `contract-ci / backend` green.

**Platform PRs.** Port-after (until a feature is shipped on Android): the iOS agent implements against the merged contract as today and must still add the scenarios; the Android port agent later ports from the spec + the iOS diff + the correspondence table + **the divergence file, which it reads first so that an iOS-only fix is not ported by mistake**, in its own PR. That PR may set the Android cell to `shipped`, and the `Parity gate` job decides whether it stays so. Parallel (once a feature is shipped on both): two agents from the same merged spec in two worktrees (`worktree-setup.sh` copies `Secrets.swift`, `GoogleService-Info.plist`, `google-services.json`, `local.properties`); `parity-merge.sh` creates `claude/<F-id>` from `main`, merges both (they touch disjoint directories; `shared/` edits happen only in the contract PR) and opens the one PR that may merge. The **port agent** (`.claude/agents/port.md`) is symmetric — either platform can be the source, "cheaper platform first" recorded in the spec — and when the port reveals a spec gap or a source-platform bug it does not diverge silently: it opens a spec PR or an issue and marks the item `blocked:<issue>`, or records a divergence.

**Parity reviewer** (`.claude/agents/parity-reviewer.md`): read-only; receives the spec, both diffs, both scenario reports, the contact sheets and the divergence entries; writes one line per spec rule with code anchors on both platforms, per scenario (green/red per platform), per test id **with its label and role on each platform**, per string key, compliance flag and fragile invariant; lists every divergence it relied on; checks that nothing changed outside `android/` (or `NaarsCars/`) plus `shared/parity/`. Run locally through `/parity` or in CI through `anthropics/claude-code-action` (§7 A6). Advisory: the ledger check and the `Parity gate` job are the mechanical gate, the owner's merge is the human one.

**Manuals.** Root `CLAUDE.md` becomes the short monorepo manual (layout, the universal rules: worktrees, public repo, migration discipline, contract-first order, the ledger, one backend change at a time, where each platform's work runs); the current 100 KB iOS manual moves to `NaarsCars/CLAUDE.md`; `android/CLAUDE.md` mirrors it section by section (lanes: cloud session and CI only, verification loop, fragile systems, canonical entry points with Kotlin names, Konsist rules, Room schema rule, the `PendingIntent` and explicit-receiver requirements, what not to port); `shared/CLAUDE.md` holds the contract and fixture conventions. Claude Code loads nested `CLAUDE.md` files by directory, so an Android session never carries the iOS manual. v1 stopped there; four more files are iOS-only today and would mislead an agent in a two-platform repository:

- **`AGENTS.md`** is titled "Naars Cars iOS — Project Instructions (Codex)", says its rules "apply to all work in this repository" and mandates `ObservableObject` view models (`AGENTS.md:1`, `:3`, `:9`). It is rewritten as the short monorepo manual for Codex with a nested `NaarsCars/AGENTS.md` and `android/AGENTS.md`.
- **The always-on Cursor rule** `.cursor/rules/naars-cars-project.mdc` (`alwaysApply: true`) is scoped to `NaarsCars/**`, and an `android/**` rule is added; the other eight rule files already use iOS globs.
- **"Do not add tests unless explicitly asked"** is in both manuals (`CLAUDE.md` Build and Test Commands; `AGENTS.md:44`). This plan depends on the opposite. The rule is replaced on both platforms by: tests are added where the Testing Expectations table, the spec's rules and the ledger require them, and nowhere else.
- **`/preflight`** scans only iOS-sensitive paths. It gains the Android list: `AndroidManifest.xml` permissions and `exported` components, `build.gradle(.kts)` `signingConfigs` / `minSdk` / `targetSdk` / new dependencies, `google-services.json`, keystores, `network_security_config.xml`, the backup rules.

One correction to the manual itself, found by the review: CLAUDE.md's fragile system 2 gives the send path as `MessageSendManager → MessageSendWorker → MessageService`. The code sends inline from the manager and uses the worker as a recovery drain (§3.6). The iOS manual is corrected when it is split, so the Android manual is not written from the wrong sentence.

**Hooks and commands.** `.claude/settings.json` gains a PostToolUse hook running `check-ledger.py --quick` when a file under `shared/parity/**` or `shared/specs/**` is written and `check-registry.sh` when a registry source is written; Bash allow-list entries for `./gradlew` and `maestro` (cloud sessions). New commands: `/spec`, `/contract`, `/parity`, `/scenario`, `/port <F-id> <platform>`, `/android-test`. The stale step notes in `headless-test.md` / `preflight.md` (tooling map §7) are fixed in phase 0.

**Where Android work runs: cloud sessions and Linux CI, never the Mac.** v1 allowed "headless on the Mac at most". The Mac has no Android toolchain and no room for one beside Xcode (§3.4), so v2 removes that lane: Gradle, the emulator, Konsist, the instrumented tests and Maestro run in cloud Claude Code sessions and on `ubuntu-latest` (about a tenth of the per-minute price of the macOS minutes iOS already spends); manual QA is on one physical Android phone (§7 C7); the signed bundle is built by `release-android.yml`. The Mac stays for iOS. Because an agent on the Mac cannot regenerate the snapshot or run the stack, it relies on the CI artefact (§3.4 #9) and on the one-backend-PR rule to avoid a rebase-and-round-trip per concurrent contract change.

### 3.11 Android release path, permissions and compliance (new in v2)

v1's release process was one line ("Play Console app, signing keystore, internal testing track ≈3 h"). Nothing produced a signed bundle, and a store requirement that can add weeks was missing.

1. **Account type and the closed-testing requirement.** A personal Play developer account created after 13 November 2023 cannot publish to production until it has run a closed test with at least 12 testers opted in for 14 consecutive days and has then applied for production access, a review Google says usually takes a week or less (**panel**, Play Console Help answer 14151465, read 2026-10-07; confirm the current numbers in the Console). An organization account, which needs a D-U-N-S number, has no such gate. The legal documents name an individual as the operator (`Legal/PRIVACY_POLICY.md:11`), so a personal account is the likely default. Every current member joined through an iPhone, so the testers must mostly come from outside the community, and v1's fallback ("the owner's second device") is one tester, not twelve. Plan (§7 D14): decide the account type before phase 5; with a personal account, recruit the testers during phase 6, start the 14-day clock when phase 7 ends (the first build worth testing), and put the production-access application on phase 9's critical path with its own one-to-two-week duration. The tester list and dates go in `releases.yaml`.
2. **What each track needs.** Internal testing (phase 5) needs only the app and up to 100 named testers. **Closed testing needs the store paperwork**: a completed Data Safety form, a privacy-policy URL, the account-deletion URL, the App access declaration and a content rating *(Play requirements, not re-checked)*. v1 scheduled all of that for phase 9; it moves to the end of phase 7, which also means the domain and static hosting of §7 D15 must exist by then.
3. **Signing.** Enrol in Play App Signing with the first upload. The upload key is generated once, kept in the owner's password manager with an encrypted offline copy, never in the repository. Two fingerprints of the **Play app-signing** certificate (not the upload key's) are copied from the Console: SHA-256 into `assetlinks.json`, and SHA-1 into the Maps and Places key restriction and the Google sign-in Android OAuth client. Registering the upload key's fingerprint instead is the usual first-release failure: sign-in and maps work in debug builds and fail in the build Play distributes.
4. **Who builds the bundle.** `release-android.yml`: manual dispatch on a train tag, in a GitHub Environment (`play-release`) whose secrets are the upload keystore, its passwords and `google-services.json`; it runs `:app:bundleRelease` and uploads the `.aab` as an artefact, which the owner uploads in the Play Console. No machine the owner works on needs the Android toolchain. A leaked upload key can be replaced through Play support because Play holds the signing key.
5. **Version scheme.** `versionName` is the iOS `MARKETING_VERSION` of the train; `versionCode` is `train × 100 + build`, strictly increasing; both are written to `releases.yaml` by the workflow.
6. **Declarations checklist** (gate for closed testing, re-checked before production): Data Safety (generated, item 8); privacy policy URL; account-deletion URL and in-app path; **App access** — the app is login-gated user-generated content, so reviewers get a seeded, approved account and a note that guest mode exists; content rating questionnaire; ads declaration (none); target audience; the UGC affirmations (report, block and moderation exist on every surface, P9); store listing in the six languages; the pre-launch report read and its accessibility warnings triaged.
7. **Permission matrix** (also a block in the spec template). iOS declares six usage strings (camera, photos, location, Face ID in `project.pbxproj`; calendar and microphone in `Info.plist`); Android needs fewer:

| Capability | iOS | Android manifest | Runtime prompt |

8. **One data inventory for both stores.** v1 pointed the Data Safety form at `Legal/PRIVACY-DISCLOSURES.md`, which is an iOS document (Info.plist keys and App Store privacy labels) that names none of the SDKs Android adds, and the iOS privacy manifest's missing data types are already an open finding. `shared/compliance/data-inventory.yaml` has one row per data type — collected, shared, purpose, SDK or processor, the iOS privacy label and manifest entry, the Play Data Safety answer. An agent drafts; the text is the owner's to approve. If the App Store privacy label has to change, that is flagged under the CLAUDE.md compliance checklist.

### 3.12 Accessibility parity (new in v2)

v1 treated test ids as if they were accessibility. They are not: a `testTag` is not read by TalkBack, and nothing in v1 would have failed an Android app that passed every gate and could not be used with a screen reader. iOS today has 147 `.accessibilityLabel(` and 65 `.accessibilityHint(` modifier calls in `App/`, `Features/` and `UI/`, plus label assignments in the UIKit messaging views (**verified v2**), and both manuals require a label on every interactive element.

- **One file, both platforms.** Each entry of `test-ids.json` carries `role`, `label_key` and, where iOS has one, `hint_key` and a state description. On iOS the key is the `accessibilityLabel`; on Android it is the `contentDescription` (or the visible text) with the matching `Role` and `stateDescription`. The phase 3 sweep that adds missing ids records the label key for each of them.
- **Checked on screen, not in source.** The generated screen-inventory flows assert each id is visible together with its English label. Maestro reads the accessibility text on both platforms, so one flow is the check for VoiceOver's label and TalkBack's. A control with the right tag and no label fails.
- **Checked in CI on Android.** Compose UI tests run with accessibility checks enabled (missing label, touch target under 48 dp, low contrast); `gen-tokens.py` already fails a low-contrast text pair (§3.7).
- **In the spec.** The Accessibility block lists, per control: label key, role, state, hint; the grouping policy (`accessibilityElement(children:)` ↔ `mergeDescendants`); reading order; live announcements; custom actions. Three places need explicit decisions in their specs because the platforms differ underneath: the transcript is a reversed list on Android and must still be traversed oldest to newest; a new incoming message and a toast are polite live regions; swipe-to-reply and the long-press reaction bar are offered as custom accessibility actions on both.
- **By hand.** A TalkBack pass is part of the gates of phases 6, 7, 8b and 9 — complete that phase's primary flows without looking — next to the VoiceOver pass iOS changes already owe, each recorded with a date in `releases.yaml`.
- **In review.** The parity reviewer's checklist has an accessibility line per test id.

## 7. Open decisions for the owner

Each decision lists options and a recommendation; the body of this document reads as if the recommendations are taken. v1's ids are kept. New in v2: A10, A11, B8–B10, C9–C11, D13–D19, E7–E9. Revised in v2: A3, A4, A5, A8, A9, B1, B3, B4, B7, C5, C8, D2, D6, D8, D9, D10, D11, D12, E1. The ones that change what gets built or when are E1, D14, D15, D2, D12, E7 and B4; the rest have a default an agent can take.

**A. Repository and process**

- **A1 Repository topology.** (a) Monorepo, `NaarsCars/` in place, `android/` + `shared/` added — *recommended*; (b) monorepo with an `ios/` move; (c) two repos plus a `shared` package. Also: rename `Naar-Caars-ios` → `naars-cars` (GitHub keeps the redirect; update `origin` in worktrees).
- **A2 CLAUDE.md split.** (a) Root becomes the short monorepo manual and the iOS manual moves to `NaarsCars/CLAUDE.md` — *recommended*, as its own docs commit; (b) keep the 100 KB root file and add nested manuals beside it (Android sessions would still load it when started at the root).
- **A3 Gate mode and dates.** The `android-launch` milestone date — six to seven months after the port starts on two lanes, nine to eleven on one (§6) — and whether `parity_due` is set per area (messaging last) — *recommended* — or uniformly. Independent of the date, a feature is in lockstep from the moment it is shipped on both platforms (§2.2 rule 5).
- **A4 Known-failure, deferred-mirror and exception deadlines.** How long a `known_failures` entry or a `deferred-mirror` divergence may stay (*recommended*: one train) and whether an `ahead` divergence needs a date (*recommended*: no, but a finding id).
- **A5 Platform-specific `n/a` features.** Which features are `n/a` on Android with a reason (native Sign in with Apple, Face ID lock and privacy cover, Liquid Glass surfaces, EventKit) and their Android counterparts (web OAuth, `BiometricPrompt` with device-credential fallback and `FLAG_SECURE`, tonal surfaces, `CalendarContract`), each with a `Platform notes` section in its spec.
- **A6 Parity reviewer execution.** (a) Locally through `/parity` in a Mac or cloud session (no extra cost) — *recommended now*; (b) `anthropics/claude-code-action` in CI with an API-key secret and a monthly budget. Advisory in both cases; never a merge gate.
- **A7 Who applies migrations.** (a) Today's procedure (agent through the MCP, one function per call, header APPLIED) now preceded by `contract-ci / backend` green — *recommended*; (b) a workflow applies them (needs a production database credential in Actions; not recommended while the repo is public).
- **A8 Release automation.** (a) Store uploads stay manual, gated by `release-train.yml`; the signed Android bundle is built by `release-android.yml` and uploaded by hand — *recommended*; (b) Fastlane and the Play publishing API with a service-account JSON in Actions secrets.
- **A9 Maestro iOS cadence.** (a) Nightly, on the `run-scenarios` label, and automatically for a PR that flips an iOS cell to `shipped` — *recommended*; (b) per PR (≈15–25 paid macOS minutes each).
- **A10 The merge rule on a one-collaborator repository.** (a) Required status checks only, binding administrators; no required approval and no CODEOWNERS; the owner's merge is the human gate — *recommended*, because the author of a PR cannot approve it and every agent PR is opened as the owner; (b) give agents a second identity (a machine account or a GitHub App) so that one approving review and code owners can be required.
- **A11 One backend change at a time.** (a) Enforced by the check in `contract-ci` — *recommended*; (b) a convention in the manuals only.

**B. Backend and test environment**

- **B1 Test backend.** (a) The seeded stack from the schema baseline dump: throwaway containers on Linux CI, plus the staging project of B4 for the iOS scenario lane — *recommended*; (b) Supabase preview branches (paid; need a replayable history this repo lacks); (c) a hosted project as the primary for everything (credentials at PR time for every check; no hermetic runs).
- **B2 Baseline dump mechanics.** (a) `supabase db dump --linked -s public` plus catalog-generated storage and cron files — *recommended*; (b) also dump `-s storage` if the first implementation shows it loads cleanly into the local image. Either way, the snapshot diff must cover bucket rows and `storage.objects` policies.
- **B3 Local stack on the Mac.** (a) Never — *recommended*. v1 offered an opt-in for a two-account session; with 8 GB of RAM and a simulator running, the stack does not fit, and two-device QA has a better home (E8). (b) An opt-in session with services excluded and Xcode closed, after repairing Docker's command-line links.
- **B4 Hosted staging project.** (a) One staging project, built and reset only by `staging-reset.sh`, used by the iOS scenario lane — *recommended, and required for that lane to exist* (§3.4 #11); (b) no staging: iOS scenarios run only by hand on the Mac against production test accounts, and an iOS cell's `shipped` rests on a manual pass; (c) a self-hosted macOS runner (the Mac cannot be one). v1 recommended "none"; that left the iOS lane without a backend.
- **B5 Generated code direction.** (a) JSON → Kotlin and TypeScript; Swift checked, and generated Swift types compiled into the test target only — *recommended*; (b) generated Swift into the app (`Constants+Generated.swift`, `NotificationType+Generated.swift`, `DeepLinkTable.swift`) gated by an equivalence test. (b) rewrites three high-blast seams for no behaviour change.
- **B6 Array-encoding normalisation.** (a) Record both encodings and reproduce them on Android — *recommended now*; (b) normalise both clients to JSON arrays in a later contract PR once both are on the harness.
- **B7 Push transport.** (a) Direct FCM for Android + direct APNs for iOS, two senders in `_shared/` — *recommended* (zero iOS change, `aps` control stays in the edge function); (b) route both through FCM (adds Firebase Messaging to iOS and moves `aps` into FCM's override block — a fragile-system change on iOS for no gain). Also A2–A5 of the notifications map: data-only high-priority messages with the token tied to the notification permission (yes, D16), no launcher badge (yes), keep `authenticationRequired` semantics (yes; natively at API 31), collapse keys for `new_ride` / `new_favor` / `town_hall_post` (out of scope unless wanted).
- **B8 Where the baseline dump is taken.** (a) A dispatch job on Linux with the read-only role — *recommended* (no database password on the Mac, no Docker there); (b) the owner on the Mac with Docker Desktop started once and the database password, if the read-only role turns out not to be able to dump.
- **B9 `register_push_token`.** (a) Ship it in phase 4; Android registers through it from its first build; iOS adopts it later in its own commit — *recommended* (Android never inherits the one-token-two-accounts finding; iOS risk is chosen separately); (b) both platforms in phase 4; (c) not at all.
- **B10 Kotlin RPC layer.** (a) Generated from `rpc/*.json` — *recommended* (call sites cannot drift); (b) hand-written call sites checked by the same key extractor iOS uses.

**C. Android stack**

- **C1 Local database.** Room — *recommended* (maps 1:1 onto SwiftData; exported schemas give a stronger migration guarantee than iOS has); SQLDelight's only advantage is KMP, which is not chosen.
- **C2 DI and modules.** Hilt + single `:app` module + Konsist — *recommended*; Koin or multi-module Gradle later only if build time demands.
- **C3 Navigation library.** Type-safe Compose Navigation with nested graphs per tab — *recommended* (matches the four `NavigationStack`s; deepest agent training data); Navigation 3 when it is the obvious default.
- **C4 Transcript implementation.** Compose `LazyColumn` — *recommended* (the UIKit reason, SwiftUI `List` performance, does not apply; the iMessage behaviours tuned on 2026-10-05 — composer inset, delivery status under the last outgoing bubble only, typing bubble as a transcript item, top-of-bubble reactions, 1 h time headers, 60 s series — are the acceptance list, with side-by-side video of the Swift build as the oracle); `RecyclerView` in `AndroidView` only if a measured scroll-performance problem appears.
- **C5 minSdk / targetSdk.** (a) **minSdk 31** (Android 12), targetSdk per Play's requirement at submission, 16 KB page-size compliance — *recommended*: the lock's passcode fallback, the blurred overlay, keyboard-tracked composer insets, authenticated notification actions and the backup rules all work without a second code path (§3.6); (b) minSdk 29 or 30 with the fallbacks listed in §3.6, if a member is known to be on Android 10 or 11. The decision should be taken with the current Android distribution figures in hand and by asking the handful of likely Android members what they carry; the Play Console has no data for an app that does not exist yet.

## 8. Deliberately out of scope

- **Shared client code of any kind** — Kotlin Multiplatform (K1, K2, and K3 except as the conditional E2), a shared Rust/C core, Swift on Android, Skip, Compose Multiplatform on iOS, React Native, Flutter, or a generated client SDK consumed by both apps. Sharing happens at the contract and spec level, where it is checkable and language-neutral; a shared constants *file* is the limit.
- **A BFF, GraphQL, OpenAPI or tRPC layer in front of Supabase.** The PostgREST / RPC surface is the contract; a gateway would be a third surface to keep in sync and a deploy pipeline the project does not have.
- **Routing iOS push through FCM**, a Notification Service Extension on iOS, rich push media, launcher badges on Android, collapse keys, and rebuilding the dead Town Hall batching path (notifications map §3.3); digests are a separate decision.
- **Pixel-diff golden screenshots across platforms.** The two platforms render differently by design; the lanes capture light/dark/large text and build contact sheets. Per-platform golden images are each platform's own later choice.
- **Device farms** (Firebase Test Lab beyond the free quota, BrowserStack) until the closed-testing group exists; one emulator, one simulator and one phone are enough.
- **Supabase preview branches** and repairing `supabase_migrations.schema_migrations`. The baseline dump sidesteps the history problem; reconciling the remote table is the separate, careful follow-up the handoff already names.
- **Automatic migration application from CI**, merge queues, auto-merge bots, Dependabot across both ecosystems, Danger / commit-lint. Required status checks that also bind administrators suffice at this team size; a required reviewer is not possible with one collaborator (§7 A10).
- **A localisation platform** (Crowdin, Lokalise) and a design-token build system (Style Dictionary). A 100-line exporter and a hex checker cover the stated goal.
- **Code-coverage gates and SwiftLint.** The repo has no linter by decision; Android gets `ktlint` because the stack is new.
- **Running the parity reviewer as a merge gate.** Mechanical checks gate; the model advises; the owner decides.
- **Rewriting the January PRDs and `QA/FLOW-CATALOG.md`.** They are inputs to the back-fill and are then superseded by `shared/specs`; a note in each points to its successor.
- **Fixing the open iOS findings the maps surfaced** beyond what this plan names: the three phase-0 fixes, the phase 3b changes (the idempotent insert, the owner's picks from §7 E7, scope-local sign-out if D5 is taken) and the two server fixes (left-member pushes and the badge number). Still out: `notify_messages` not enforced on the message push path, the broadcast side door, Town Hall batching, the duplicate local reminder on iOS, the privacy manifest's missing data types (the data inventory lists them; fixing the manifest is its own iOS change), the reactions gap in the post-join hydrate. They are recorded in the ledger as iOS cells, divergences or `known_failures` where a fixture encodes them.
- **Multi-community features as part of the port's own design.** Under the recommended ordering the port targets the community-aware app, but the community rules, schema and screens are specified in the multi-community design; this document only supplies the harness they go through and prices their Android twin (§6).
- **Moving the iOS project under `ios/`**, Google Sign-In on iOS (a follow-up ledger item), phone-number auth, Play Billing, widgets, Wear OS, Android Auto, tablet / foldable layouts, landscape (iOS is portrait-only too), feature flags / remote config (version skew is handled by the additive-schema rule), offline-first beyond the pending-send queue, and any difference between the platforms beyond the closed deviation list and the recorded divergences.
- **WorkManager as the message send queue**, and a WorkManager job that resends rows left `sending` after a process death (§7 D6).
- **A per-token priority hint or a report of muted channels to the push sender.** The token is tied to the app-level permission instead (§7 D16); channel-level reporting is a recorded follow-up.
- **Server-side Apple token revocation for an account deleted from Android**, which would need the refresh token stored at native link time.
- **An Android lane on the development Mac**, a local stack there, and a hosted staging project that sends real pushes (§7 B3, B4, E8).
- **Re-deriving the KMP and React Native estimates** with the tiered rates (§6).

## 9. Alternatives considered and why rejected

**`android-native-mirror.md` — "Two native codebases, one contract layer" (second place).** This is where the Android half of the synthesis comes from: the stack table, the module-by-module correspondence with per-module agent-days, the closed sanctioned-deviation list, the Konsist restatement of the fragile-system invariants, Room with exported schemas and `MigrationTestHelper`, data-only FCM with `data.category` and five channels, the symmetric port agent, the mirror-PR workflow, the phase order (messaging last, after a dated two-device pass) and the CLAUDE.md split. It was not taken as the base because its development environment was unsafe as written: its CI runs `supabase start` + `db reset` from `supabase/migrations/`, which this repo cannot replay, and it never overrides `invoke_edge_webhook`, so every seeded insert in its CI and on its proposed staging project would POST to the production edge functions; its `rpc.yaml` is specified as "the 24 client-callable RPCs" (the backend map's heading error) and would have omitted `edit_message`, `unsend_message`, `mark_messages_read_batch`, `submit_report`, `get_conversations_with_details` and the block RPCs; it bundles the scope-local sign-out — a fragile-system-5 change the owner left open on purpose — into a "backend" phase; its E5b item is mis-specified (the id is created per attempt, not per pending row); and its iOS Maestro runs are manual-dispatch only, so cross-platform scenario parity is never gated on iOS. All of those are fixed here.

*v2 note.* The review found two weaknesses in what was taken over from this design most directly. Its stack table mapped three fragile rows by name — the realtime manager to `postgresChangeFlow` "collected on Main", the send worker to a `CoroutineWorker`, the repository to "a Mutex and flows" — without checking what `supabase-kt`, WorkManager and Room do; and its per-module days did not follow its own rate rule, nor did its phases add up to its modules. Both are corrected in §3.6 and §6.

**`android-kmp-core.md` — "Native Android with a Kotlin Multiplatform shared core" (third place).** Its real contribution is the verdict and the evidence for it: every interop claim checked out (`@ModelActor`, `Task`-holding `FreshnessState`, the SwiftData send queue, `PendingMessageInfo: Sendable`, `@MainActor @Sendable` callbacks, the Keychain session that `supabase-kt` would move to `NSUserDefaults`), and the costed comparison (K1 110–145 agent-days against 72–92) is the most useful number in the set. It is kept in this document as the recorded reason no client code is shared (§1.2, §8), together with K3 as a conditional later phase (E2), the P12 version-skew rule as a migration-header line, the PAR-001..008 scenarios, the "export the live `should_notify_user` body before touching it" instruction and the rule that the first Android tests are the iOS tests ported case for case. It was rejected as the base because its recommended path still generates Swift into three high-blast seams (`Constants`, `NotificationType`, `DeepLinkParser`) for no behaviour change, proposes a hosted staging project reset nightly from the non-replayable migrations with no webhook override, is internally inconsistent on the RPC count, and recommends email-only sign-in on Android, which would lock out the Apple-only members. K1 and K2 themselves are unshippable on a live App Store app: they rewrite every High-Risk file in CLAUDE.md and the session storage for zero user-visible benefit.

*v2 note.* The PAR scenarios came with this design's assumption of one hosted backend both lanes could reach. v1 kept the scenarios and dropped the backend. v2 restores a hosted project for the iOS lane only and redefines the scenarios per lane (§2.3).

**`android-devils-advocate.md` — "Devil's advocate for a unified stack" (fourth place).** It makes the strongest honest case for React Native + Expo — system chrome through `react-native-screens`, `expo-glass-effect`, APNs categories incl. text-input reply and `authenticationRequired`, SIWA via `signInWithIdToken`, and uniquely a web client — and then shows it loses: a 160–225 agent-day rewrite that reaches Android no sooner than a native port, 85–90 % fidelity on the UIKit transcript, re-implementation from zero of account deletion, moderation, SIWA and the privacy manifest (every previously-fixed App Store rejection class), loss of `default.store` pending sends and Delete-for-Me markers without a native importer, and the end of compile-time actor isolation as a correctness tool. The synthesis keeps its decision list rather than its design: D1 (a web client is the one input that would change the verdict — decide before phase 5), D12 (freeze iOS features during the port and build multi-community once per platform afterwards), the storage finding (every bucket public, unfiltered `message-images` INSERT) that puts the `storage` schema into the snapshot, generating the SQL CHECK body from the registry, the correction that the client already sends a message id (refined here, §1.3), and the unused `geocoding_cache` as a shared cache. It was rejected as the base because its two-native plan is a paragraph, its contract layer is shallower than the harness's (no probes, no conformance runner, no ledger, no webhook treatment), its two-native cost (135–180 agent-days) is not derived per module, and its unified path — had it been taken — would have been fatal to the App Store non-negotiables.

*v2 note.* Its D12 — freeze iOS feature work and build multi-community once per platform after the port — is still listed (§7 E1, option B) but is no longer the recommendation, for the reason given in §1.3.

**`android-parity-harness.md` — the base, with its own flaws fixed.** Its baseline-dump command used a `--schema-only` flag that does not exist (schema is the default; `-s` selects schemas — verified against CLI 2.67.1), its dump omitted the storage policies and bucket rows that private communities must later close, its "PR must commit the post-migration snapshot" rule was circular for an agent without Docker on the Mac (CI now produces the artefact), it stated "125" for the count of multi-specifier strings (27; 125 is the count with at least one specifier), and it deliberately left the Android stack to another design. The review then found four more: its ledger gate keyed on a status label an agent sets; its scenarios signed in through a launch argument no code reads while it promised not to touch the auth path; its iOS scenario lane assumed a container runtime the macOS runners do not have; and its realtime fixtures were built around shapes no client receives. Those are fixed in §2.2, §3.3, §3.4 and §3.8. What stands as written: contract-first order, the generated snapshot with function-body hashes, per-RPC `arg_encoding`, versioned row fixtures, pgTAP probes lifted from the migration headers, the RPC conformance runner, deno edge tests with mocked `fetch`, the nightly live-drift job, port-after with due dates and `known_failures`, and the path-filter-inside-one-job CI rule. Its DEBUG-only backend override is no longer needed (§3.4 #10), and its harness cost of about 41 agent-days is now about 44 with the review's additions.

**Alternatives the review proposed that v2 did not take.**

- *Restart the send worker after every optimistic insert, and treat "failed after about 15 s" as the iOS reference* (ARCHITECTURE-3's recommendation). The panel showed the premise is wrong: iOS sends inline once and fails at once, and the worker only drains at session start and on network restore. A per-insert drain beside an inline send would send every message twice.
- *Rate all 24,518 messaging lines at the fragile rate* (COST-1's 40–50 agent-days). CLAUDE.md names specific files; the gallery, the report sheet and the logger are not fragile. v2 uses the tiered figure, 35–41.
- *A DEBUG test-session hook that signs in a seeded user* (PARITY-3 option B). It is a new launch-time path in fragile system 5 to save a few seconds per scenario; the login subflow costs nothing in the app.
- *Scenario results committed as files keyed by the head SHA* (PARITY-2). Committing the file changes the SHA it is keyed by; the gate reads the lane's report within the same run instead.
- *Four refactor-only iOS PRs before the port, including a single mapper for the Ride and Favor field lists* (COST-6). Three of the four are offered in §7 E7; the mapper extraction rewrites a High-Risk file for tidiness and is replaced by a round-trip test on both platforms.
- *A network-kill Maestro scenario for reconnects* (ARCHITECTURE-7). Maestro cannot take the iOS simulator offline; the `rejoin` sequence fixture covers the logic on both platforms and the two-device pass covers the real thing.
- *A per-token `notifications_enabled` column so the sender can lower priority* (PLATFORM-3). Not holding a token while notifications are off achieves the main effect with no schema change.

### Rejected review findings

- **ARCHITECTURE-2** — Rejected as stated, by all three refuters. The claim was that the repository mapping "cannot reproduce" a synchronous upsert and conversation-keyed publishers. The design mapped the messaging publishers to repository-owned flows, not to Room-observed queries (the Reads row mirrored the two iOS screens that use `@Query`); a Mutex is the right substitute for "no suspension point"; and two of the three examples were wrong (the send worker's replace re-emits the list on iOS too; `excludeMessagesForConversation` exists to avoid concurrent writes, not to limit emissions). The low-severity wording gap all three refuters named is closed anyway: the repository row now says in so many words that messaging flows are repository-fed and never Room-observed, that the Mutex spans the transaction and the emission, that `replaceOptimisticMessage` is one transaction, and the sequence fixtures pin the metadata-only path, which no iOS test pins today.

### Found while revising (not raised by the review)

1. v1's DEBUG backend override could not have served the iOS scenario lane even as designed — Maestro passes launch arguments, not environment variables — and it was unnecessary: `ios-ci.yml` already writes `Secrets.swift` from two values.
