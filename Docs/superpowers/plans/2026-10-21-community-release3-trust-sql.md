# Community Release 3 (trust): Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every request an area that stands in for its addresses, keep addresses for the poster, the poster's participants, the connected helper and platform admins, add offers in open communities with poster-only decisions, request threads that close when the connection ends, a poster-only Q&A answer, a 24-hour cool-off in open communities and four new notification types, shipped as an additive step (3a, applied now) and a gated flip (3b, written and dry-run now, applied only at its gate).

**Architecture:** 3a adds columns, a `BEFORE INSERT OR UPDATE` trigger that derives each area on the server from a client-sent point and label, SECURITY DEFINER RPCs for offers, answers, request threads and reach, two `security_invoker` member views (`member_rides`, `member_favors`) that still return addresses to every member, and the registry and badge changes. 3b swaps the views to return areas unless `my_request_addresses()` returns the row, replaces table-level SELECT on `rides` / `favors` with a column grant that leaves out the address and exact-coordinate columns, retires the direct claim policies, allows `'open'`, switches messaging reach and every address-carrying server text to areas. Old builds see nothing in 3a; 3b breaks every build older than Release 3, hence its gate.

**Tech Stack:** PostgreSQL 15 on Supabase (plpgsql, RLS, column privileges, `security_invoker` views, pg_cron), the Supabase MCP (`execute_sql`, `apply_migration`), `supabase/probes/communities_probe.sql`.

**Spec:** `Docs/superpowers/specs/2026-10-21-community-discovery-and-trust-design.md` (4.4, 4.5, 4.6, 4.7, 4.8 and the 4.10 "Release 3" paragraph). The iOS plan `Docs/superpowers/plans/2026-10-21-community-release3-trust.md` consumes the interfaces listed at the end of this file.

## Global Constraints

- **The server is the boundary** (spec 3): who sees an address, who may offer, message, post or ask is decided by RLS, views, triggers or SECURITY DEFINER RPCs; screens only explain.
- **Every new function:** `set search_path = ''`, every name schema-qualified, `revoke all … from public`, EXECUTE granted only to the roles named in its block; caller-bound helpers answer only for `auth.uid()` (CLAUDE.md, database contract).
- **An RPC whose signature changes gets a new name** (spec 3). A function edited in place keeps its signature and starts from the **live** body (`pg_get_functiondef`), md5-checked before and after.
- **A column added to `rides` or `favors` is added to every view over them in the same migration** (CLAUDE.md, Audit Notes); after 3b it also needs a column-level `grant select (…) … to authenticated` in that migration.
- **The MCP declines** `DELETE`, `DROP POLICY`, `DROP FUNCTION`, `DROP TABLE` and auth/storage deletes. Those statements live only in File G (owner, SQL editor), verbatim, never rephrased. `ALTER POLICY`, `REVOKE` / `GRANT`, `ALTER TABLE … CONSTRAINT`, trigger DDL and `CREATE OR REPLACE FUNCTION` go through the MCP, **one `apply_migration` per block, one function per block**.
- **Every apply is preceded by a rolled-back dry run** (the Phase 5 SQL plan's assembly: PARAMETERS and HELPERS without their `commit;`, `begin;`, the blocks, the probe blocks as savepoints, `select 'DRYRUN … OK';`, `rollback;`) and followed by `short` and the file's probe blocks.
- **Headers** follow `20261019_0050`: NOT APPLIED until applied; then APPLIED with date, migration-history versions, `md5(prosrc)` of each function (equal to the text between its delimiters), view digests, probe outcomes, what old clients see, rollback per block.
- **Notification registry: 34 → 38 types** (`offer_received`, `offer_accepted`, `offer_declined`, `offer_withdrawn`). File B (S2) widens only the SQL CHECK and the server functions; the TypeScript constants, the Swift enum and `NotificationTypeRegistry`, and the script's `SQL_CHECK_FILE` default (→ File B) land in one commit, iOS Task 12, so `scripts/validate-notification-types.sh` prints "34 types in sync" at every commit before it (it reads `20261019_0001` until then) and "38 types in sync" from it on. No producer of the four types runs before then (offers need offer mode, which needs an open community or an orchestrator's test row at the 3a gate).
- **Public repository.** No personal data in committed SQL, headers or probe output (ids at most the first 8 characters already in `Docs/qa/test-data.md`). Files F and G describe what 3a leaves open (addresses still readable by members); they are committed locally and pushed only with the owner's yes (CLAUDE.md, Current State).
- **SQL apply authority:** the owner's standing instruction for the multi-community build covers 3a. 3b is applied only at Task S8's gate.
- Commits: subject `[R3-S<n>] …`, body ending `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>` (an executing session whose harness gives another attribution line uses that one). **Staging:** `git add` exactly the task's **Files** paths, which each commit step names; never `git add -A` or a directory; tasks never push.

## Review Focus

1. **The A5 backfill touching every live request** (an UPDATE of rows people are using: an enabled UPDATE trigger that notifies, queues a push, writes XP or bumps `updated_at` would fire once per row). Expected: no `notifications` or `notification_queue` row, `updated_at` unchanged, both areas filled. Pinned: P10 (every enabled UPDATE trigger classified in File A's header; the ones that act on any update are disabled around A5) and probe `trust_areas` (A5's statements run in a savepoint: counts and `updated_at` unchanged).
2. **Two writes racing on one request** (the poster accepts while the helper withdraws; two members claim one claim-mode request; the poster accepts two offers back to back). Expected: exactly one helper; the loser gets `request_taken` / `offer_not_pending` / `not_open`, never a second `claimed_by`. Pinned: every RPC that changes a request takes `select … for update` on it first (Task S4), and probe `trust_offers` checks the second accept and the claim after an accept.
3. **A request that ends or moves under pending or accepted offers** (deleted, expired by the nightly job, its community merged into another, the poster's account deleted, the helper leaving or removed). Expected: pending offers end `closed` or `withdrawn`, each helper is told once, the request thread closes, a merged request's offers move with it, no FK error. Pinned: probe `trust_offers` (delete, `expire_past_open_requests()`, the merge, `leave_community`, `delete_user_account`).
4. **Area inputs a client controls** (no point, an out-of-range point, a label with digits or over 40 characters, a poster PATCHing `pickup_area_lat` directly, an edit that changes only the notes). Expected: the exact point lies inside the circle, the circle never moves on an unrelated edit, a client-set circle is reverted. Pinned: probe `trust_areas`.
5. **The 3b flip:** an invoker function, trigger or policy that reads `*` or an address column of `rides` / `favors` after the revoke; a grant list missing a column (a decode failure for every member) or still granting an address column; an open community hidden by any path. Expected: every question, review and participant insert still works; `has_column_privilege` is true for every column except the six (rides) and three (favors) address columns; hiding an open community answers `invalid` or falls back to Ask to join, never a CHECK exception. Pinned: Task S6 P8 query, File F block 4's assertion `DO` block, and probe `trust_flip` (the question and review inserts after the flip, the privilege matrix, the unlisting cases).

- **Writes:** inserts and edits keep writing the tables and send `pickup_lat`, `pickup_lng`, `pickup_area` (label input), `destination_*`, `location_*`; they return `select=id` only and read the row back through the view.

## Deviations and choices the owner can veto

- **D-R1. Cool-off reads `activated_at` only.** A member approved in the 24 hours before an approval → open switch keeps the rest of their 24 hours (the spec's "no cool-off for existing members" holds for everyone else); pending people admitted by the switch get the full 24 hours. The alternative (an `open_since` column) costs a column and a trigger for a rare case.
- **D-R2. One radius per end** (`pickup_area_radius_m`, `destination_area_radius_m`), not one per request: one end can fall back to the community circle while the other has a point.
- **D-R3. `release_helper` works in every mode**, and a poster's release or own acceptance never notifies the poster (`naars.skip_poster_status_notice`); the released helper is told with `offer_declined` / `released` even in a claim-mode request.
- **D-R4. A `not_chosen` or `withdrawn` helper may offer again** after the request reopens (their row is reopened); a `declined` one may not (spec 4.5).
- **D-R5. The narrowed reach is used in 3a** by `can_message_user` and `search_reachable_members` (identical to today's reach while no open community exists); policies switch only in F7.
- **D-R6. House-number refusals:** offer notes and answers from 3a (new RPCs, Release 3 clients only); questions, ride notes, favor titles and descriptions only from 3b, so a Release 2 build is not refused in 3a. False positives such as `'Gate 12 Pike Place'` are accepted (the person rewords).
- **D-R7. The Q&A closes on the server when a helper is connected** (C13) in every mode; today only the client hides the field.
- **D-R8. `get_trust_features()`** is a server switch the client reads, so the Release 3 build offers Open and the "only then are addresses shared" sentences the moment 3b is applied, without another release.
- **D-R9. The backfill runs in 3a** (A5), not with the flip: it is invisible to old builds and lets the Release 3 client show areas for older requests before 3b.
- **D-R10. Guest views keep `''` addresses until 3b** (A4 only appends the area columns), as the spec splits it; the Release 3 client already draws the areas from the new columns.
- **D-R11. The `area_circle` offset is seeded with the public request id.** Anyone with the id and this file can undo the 400 m offset, so what hides the exact point is the 0.01° grid cell (about 1.1 km by 0.75 km at Seattle's latitude) inside a 1207 m circle. A server-only random seed column was not added: every member and guest view and the 3b grant list would have to leave it out, against the rule that a new `rides` / `favors` column joins every view.
- **Follow-ups, not in this release:** `my_request_addresses()` returns every row for a platform admin (fine at today's ~170 requests; revisit with town-sized communities); `edit_message` / `unsend_message` in a closed thread are not refused; dropping `get_conversations_with_details` is not needed (unchanged).
